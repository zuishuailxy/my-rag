# 记忆检索配额熔断（429 快速失败）

> 状态：已批准，实施中
> 日期：2026-10-29
> 关联：`docs/benchmarks/README.md` 结果七、`docs/specs/2026-10-29-Mem0两层检索并行.md`

## 1. 问题

### 1.1 现象

补测流式分段埋点时（75 条样本）出现：

| 项 | 值 |
| --- | --- |
| 命中 `MEM0_SEARCH_TIMEOUT_MS=1500` 预算超时 | **57 / 75（76%）** |
| app 日志 `429 Too Many Requests` | **69 处** |
| 配额 | `1000 / 1000` 已用尽，`quota_reset = 2026-11-24` |

### 1.2 异常形态（实测，非推测）

不设预算直连 6 次，全部 429：

```
type   : mem0.exceptions.RateLimitError
mro    : RateLimitError → MemoryError → Exception
str    : {"error":"Monthly retrieval limit reached (1000 of 1000). ...",
          "quota_limit":1000,"quota_used":1000,"quota_reset":"2026-11-24T00:00:00+00:00"}
属性    : 无 status_code / response / body；有 message、error_code(="HTTP_429")
单次耗时: 270 ~ 1449ms
```

**更正前一轮的说法**：提交 `9f18e37` 的说明里写「SDK 退避重试把它拖到预算边缘」，这是错的。
`grep -rn "retry|backoff|sleep" --include=*.py .venv/.../mem0/` 为空，`AsyncMemoryClient.search()`
只有一次 `POST` + `raise_for_status()`。那 270~1449ms 是**走本机代理到 `api.mem0.ai` 的单次往返**，
不是重试。结论方向不变（都在白等），但归因必须改。

### 1.3 两个后果

1. **每轮白等一次往返**。配额耗尽后每一轮对话都要为「确定查不到」付 0.3~1.4s，
   这段还坐在 TTFT 关键路径上（`build_system_message` 无条件注入）。
2. **把「不可用」伪装成「慢」**。上一轮就是被它骗的：`spans.memory` 贴着 1500ms 预算
   （p50 1507 / max 1802），看起来像「记忆检索很慢」，实际是「429 失败了」。
   运维看到的现象是性能问题，真因是额度问题。

## 2. 目标与非目标

### 目标

| 编号 | 目标 | 判据 |
| --- | --- | --- |
| G1 | 配额耗尽后**不再发出网络请求** | 熔断窗口内 `client.calls` 不增，耗时 ≈ 0 |
| G2 | 每次熔断只打 **1 条** WARN，且可操作 | 内容含「配额耗尽」「更换 MEM0_API_KEY」，附跳过次数 |
| G3 | 窗口结束后自动再探，**不需要重启进程** | 窗口过期后下一次检索重新发请求 |
| G4 | 429 不再被记成「某层检索失败」 | 日志里无 `Mem0 user 层检索失败：…429` |

### 非目标

- 不改 SDK、不 monkey-patch 客户端内部；
- 不改 `MEM0_SEARCH_TIMEOUT_MS`（预算仍然兜「慢」，与「没额度」是两件事）；
- **不解析 message 里的 `quota_reset` 去定死解封时间** —— 那等于「到 11-24 之前永久关闭记忆」，
  换 key 或提额后也不会恢复，只能重启。固定窗口每次只多付一次探测成本，却能自愈；
- 不动 `remember_turn` 的写入路径。`add` 打的是另一个端点、另一条配额
  （报错里 `event_type: SEARCH`），本次不臆测它的行为。

## 3. 需求

| 编号 | 需求 |
| --- | --- |
| R1 | 识别 429 用**类型**判定：`isinstance(err, mem0.exceptions.RateLimitError)`；兜底看 `error_code == "HTTP_429"`。**不做 message 子串匹配** —— 用户的检索词里带 `429` 就会误判 |
| R2 | 任一层 429 即按「整体不可用」处理：返回空，不再拼半份记忆（配额是账号级的，一层 429 另一层必然也 429） |
| R3 | 触发后打开 `_QUOTA_COOLDOWN_S = 600`（10 分钟）窗口，窗口内 `search()` 在发起请求前直接返回空 |
| R4 | 窗口内被跳过的调用只累加计数，**不打日志**；下次熔断时把这批计数一并写进那条 WARN |
| R5 | 非 429 的异常维持原行为：单层降级、按层 WARN、**不**打开熔断（否则一次网络抖动会关掉记忆 10 分钟） |

## 4. 接口与行为

`search()` 的签名、返回类型 `LongMemoryHits`、调用方全部不变。变化只在内部时序与日志。

```
search()
 ├─ 未配 key            → 空（原行为）
 ├─ 熔断窗口内          → 空，0 次网络请求，跳过计数 +1     ← 新增
 ├─ 两层同发（asyncio.wait + 预算）
 │    ├─ 任一层 429      → 打开窗口 + 1 条 WARN，空          ← 新增
 │    ├─ 有任务未完成    → 不取消！挂回调等它跑完：
 │    │                    └─ 跑完是 429 → 开窗（记给下一轮）← 新增
 │    │                    └─ 跑完是别的 → 什么都不做
 │    │                    └─ 本轮按超时返回空 + WARN 超时（原行为）
 │    ├─ 其它单层异常    → 只降级该层，按层 WARN（原行为）
 │    └─ 全部完成        → 按层解析
 └─ 调用方取消          → 连在途请求一起取消（保持原语义）
```

## 5. 边界与失败模式

1. **进程重启即解封**：状态在实例上（`chat_long_memory_service` 是单例），不落盘。
   这是刻意的 —— 重启后重新探测一次的成本远低于维护一份持久化状态。
2. **窗口是固定 600s，不对齐 `quota_reset`**：配额真正恢复（换 key / 到重置日）后，
   最多多等 10 分钟才恢复记忆，不需要人工干预。代价是配额仍耗尽时每 10 分钟白付一次往返。
3. **同一时刻多个并发请求都 429**：第一个 trip 打开窗口，后续的 trip 只顺延窗口、
   **不重复打日志**（`_trip_quota_breaker` 里判「窗口是否已开」）。`trip` 全程无 `await`，
   单线程事件循环下不会出现半开状态。
4. **429 比预算慢（实施中改掉的一条）**：原设计认为「超时先到 → 熔断不打开，只多付一轮」可接受。
   实测推翻：429 单次往返 309~979ms（绕代理后），冷启动握手更久，会**经常**比 1500ms 预算慢；
   连续 4 次里只有 1 次撞上。若维持原设计，熔断能不能生效取决于「429 是否刚好比预算快」，
   换台机器行为就变。**改为超时不取消在途请求**，挂回调等它跑完再判定（见 §8）。
5. **`_layer_payload` 不再收到 429**：配额检测在解析前返回，所以已有的「按层 WARN」
   不会把账号问题写成检索故障（G4）。

## 8. 实施记录（计划外的两处改动）

### 8.1 为什么把 `asyncio.timeout + gather` 换成 `asyncio.wait`

第一版按 §4 原图实现后，用真实 key 连跑 6 次：

```
第 1 次: 1502.0ms   ← 超时
第 2 次: 1501.9ms   ← 超时
第 3 次: 1502.1ms   ← 超时
第 4 次: 1093.7ms   ← 429 这次比预算快，才开窗
累计被跳过: 0 次
```

熔断 4 次只触发 1 次 —— **功能写了但基本不生效**。原因是 `asyncio.timeout` 到期会取消子任务，
而 429 的往返常常比预算还慢。`asyncio.wait` 不取消未完成任务，于是可以在预算之后才看到 429，
把账记给下一轮（本轮该放弃还是放弃）。代价：超时轮次的请求会在后台多跑约 1~2 秒才结束，
`_inflight` 持强引用防 GC；调用方主动取消时仍会连它们一起取消。

### 8.2 一个只有真跑才看得见的缺陷

第一版用 `any(_task_is_quota(t) for t in done)` 判配额。生成器**在第一个 True 处短路**，
第二个 task 的异常没人取回，事件循环关闭时打：

```
ERROR asyncio: Task exception was never retrieved
future: <Task finished name='Task-3' coro=<AsyncMemoryClient.search() ...> exception=RateLimitError(...)>
```

单测抓不到（它只影响 GC 时的日志），是连跑 6 次时在输出里发现的。改成 `for` 循环走完所有
`done`，顺带把每个异常都取回。

### 8.3 变异验证结果

| 变异 | 结果 |
| --- | --- |
| 删掉熔断快路径（窗口内仍发请求） | `test_breaker_skips_network_for_later_turns`、`test_suppressed_count_reported_on_next_trip` 变红 |
| `_is_quota_error` 改成 `"429" in str(err) or "limit reached" in str(err)` | `test_text_mentioning_429_is_not_quota`、`test_quota_detection_covers_error_code_fallback` 变红 |

第二条第一次做时**没变红**——因为假 429 的文案里正好含 `limit reached`。补了「文本里有 429
但不是配额错误」这条反向用例后才抓得住。这就是「测试通过 ≠ 断言有效」的现场例子。
