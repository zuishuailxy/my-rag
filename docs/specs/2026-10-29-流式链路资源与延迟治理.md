# Spec：流式对话链路的连接占用与首字延迟

> 状态：已实施（2026-10-29，验收记录见 §9）
> 日期：2026-10-29
> 关联：`docs/benchmarks/README.md`（2026-10-29 修复前 / 修复后两批实测）、`docs/architecture/AgenticRAG流程.md`

## 1. 问题（全部有实测证据）

### 1.1 一条 PG 连接被占满整轮对话

`chat_session_service.create()` / `touch_title()` 末尾的 `session.refresh()` 会在 `commit()`
之后**重新打开事务且不再提交**。对本机连接池 `checkedout()` 实测：

| 动作 | checkedout | 事务中 |
| --- | --- | --- |
| 执行 SELECT | 1 | True |
| `commit()` | **0** | False |
| `refresh()` 式再读 | **1** | True |
| `close()` | 0 | False |

而 `stream_chat` 拿到的 `db` 来自 `Depends(get_db_session)`，FastAPI 的生成器依赖活到**整个流结束**。
于是第 50ms 占住的连接一直放到第 4600ms：

```
50ms   refresh 占住连接 ──────────────────────────────────────┐
50ms   ~1650ms  classify（外部 LLM）                          │ idle in transaction
1650ms ~3500ms  Mem0 检索（外部 HTTP）                        │
3500ms ~4600ms  agent 流式                                    │
4600ms 落库 ─────────────────────────────────────────────────┘ close
```

### 1.2 后果：池耗尽被伪装成「处理很慢」

池 = `DB_POOL_SIZE 20 + DB_MAX_OVERFLOW 10 = 30`，`DB_POOL_TIMEOUT = 30s`。
并发 40 时需要 40 条连接抢 30 条 → 等满 30s 超时 → **p50 记录成 32.57s**。
这个数字是排队时间，不是处理时间；任何引用都必须写明。

### 1.3 Mem0 检索共用 60 秒超时，且坐在关键路径上

`chat_long_memory_service` 没有自己的超时，检索直接受 `AI_CHAT_TIMEOUT_MS = 60000` 约束。
一次慢请求就能把首字拖到 60 秒——而记忆只是背景信息，不值得让用户等。

### 1.4 TTFT 4.6 秒里，自己的代码只占 5%

| 阶段 | p50 | 占 TTFT | 归属 |
| --- | --- | --- | --- |
| `memory`（Mem0） | 1847ms | 40% | 外部依赖 |
| `classify`（意图路由） | 1653ms | 36% | 外部依赖 |
| `summary` | 174ms | 4% | 自己的 IO |
| `stream`（mock 模型） | 68ms | 1% | 模型 |
| `session`/`history`/`prepare` | 57ms 合计 | 1% | 自己的代码 |

且这两段外部依赖**互不依赖**，却串行执行。

## 2. 目标 / 非目标

### 目标

| 编号 | 目标 | 度量方式 |
| --- | --- | --- |
| G1 | 单请求占用 PG 连接从 ~4.6s 降到 <150ms | 集成冒烟读 `engine.pool.checkedout()` 峰值 |
| G2 | 并发 40 不再出现 `QueuePool limit` / `pool_timeout` | 压测失败数为 0，p50 不再出现 ~30s 平台 |
| G3 | 压测口径 TTFT p50 从 4626ms 降到 ≤2000ms | 同口径重跑 `--out` |
| G4 | Mem0 检索最坏 1500ms，超时降级为空记忆 | 单测 + 日志 |
| G5 | 埋点仍能分别回答「用户等了多久」与「这段本身多慢」 | 日志同时含 `stages` 与 `spans` |

G3 的算术依据（压测口径，mock 模型）：
`session 38 + history 13 + summary 174 + max(classify 1653, mem 1500) + prepare 6 + stream 68 ≈ 1952ms`。

### 非目标（本次明确不做）

- 不改改写窗口（12 条）、不改门控只看 `question`、不改池大小与 `DB_POOL_TIMEOUT`
- 不改「客户端断开 → 生成器被取消 → 落库丢失」——独立问题
- 不改非流式 `/ai/chat`（它 `append_turn` 在最后才碰库，危害小一个量级）
- 不改 SSE 协议与任何事件字段

## 3. 需求

| 编号 | 需求 | 验收 |
| --- | --- | --- |
| R1 | `stream_chat` 不再接收 `db` 参数；DB 只在「前置」与「收尾」两个 `async with async_session_factory()` 块内访问 | 函数签名 + mypy 通过 |
| R2 | 前置块在 `classify` 之前结束，出块即 `close()` 归还连接 | 集成冒烟断言 classify 期间 `checkedout() == 0` |
| R3 | `classify` 与 Mem0 检索并行，但 `intent` 帧不得因为等 Mem0 而后移 | 单测：Mem0 慢 200ms 时 intent 帧不延后 |
| R4 | 任一分支（classify 抛错、agent 为 None、客户端断开）都不得泄漏后台 task | 单测：异常路径下 task 已取消 |
| R5 | Mem0 检索**整体**预算 `MEM0_SEARCH_TIMEOUT_MS=1500`（两层共用同一 deadline）；超时 WARN + 返回空，不向上抛 | 单测：`_timeout_s=0.05` 时 50ms 内返回空 |
| R6 | `TurnTiming` 新增独立测时的 `span`，与墙钟 `stages` 并存；`stages` 之和仍≈TTFT | 单测：并行段 span > stages 中该段 |
| R7 | 对外语义不变：`session` 帧 → 历史 → `status/intent` 帧 → 正文 → `finish` → 落库，顺序与内容不变 | 现有 `smoke_ai_stream.py` 全通过 |

## 4. 接口契约

```python
# 变化
AiStreamService.stream_chat(dto: ChatStreamRequest, user: AuthUser) -> AsyncIterator[str]
ChatLongMemoryService: 新增实例属性 _timeout_s（来自 settings.MEM0_SEARCH_TIMEOUT_MS）
TurnTiming.span_start() -> float
TurnTiming.mark_span(name: str, started_at: float) -> float   # 毫秒，存入 spans

# 不变
AiStreamService.load_working_history(db, user_id, session_id)
ChatLongMemoryService.search(user_id, session_id, query) -> LongMemoryHits   # 仍不抛异常
```

配置新增：

```python
MEM0_SEARCH_TIMEOUT_MS: int = 1500   # Mem0 检索整体预算；记忆是背景信息，不值得让用户等
```

日志契约：

```
本轮耗时：sessionId=…, ttft_ms=…, total_ms=…, stages=session:38,history:13,…, spans=classify:1653,memory:1500
```

`stages` = 墙钟分段（相邻 mark 不重叠，之和 ≈ TTFT）；
`spans` = 各 span 的真实耗时（可重叠，之和可大于 TTFT）。两者不可互相推导。

## 5. 边界与失败模式

| 场景 | 期望行为 |
| --- | --- |
| Redis 热窗口命中 | 前置块只做会话行；无历史查询 |
| Redis miss 需回填 | 回填在同一个前置块内，仍早于 classify 归还连接 |
| `create` / `touch_title` 抛错 | 前置块 rollback，SSE 返回错误事件（与现状一致） |
| `classify` 抛错 | Mem0 task 被取消；异常按现状向上冒泡 |
| `agent is None`（无 LLM Key） | 取消 Mem0 task 后提前结束，不泄漏 |
| Mem0 超时/异常 | 返回空记忆，对话继续；WARN 一条 |
| 客户端中途断开 | 生成器被取消；落库不执行（**现状，本次不改**，见非目标） |
| 落库失败 | WARN，不影响已发出的回答（现状） |

## 7. 实施计划

| 提交 | 内容 | 独立可回滚 |
| --- | --- | --- |
| C1 | 短会话：DB 只在前置/收尾块内访问（R1、R2） | 是（纯资源修复，不改行为） |

若线上出现依赖顺序的问题（例如某工具隐式依赖 intent 已产出），可单独回滚而不退回连接问题。

### 9.3 偏差与不达标项（不粉饰）

1. **G3 只在并发 ≤20 成立**。40 / 100 两档 TTFT p50 是 2.31s / 5.07s，超出 2s 门槛。
   原因是**排队等连接**（池 30 在 100 并发下被打满），不是自己的处理变慢：
   同批次 p50 分别是 2.90s / 5.95s，TTFT 占其中约 80%，与修复前的比例一致。
   要把 G3 推到高并发也成立，得改池大小或加限流 —— 都是本次的非目标，**不做**。
2. **原定文件名 `2026-10-30-*.json` 与实际不符**。数据在 10-29 17:38 采集，改落
   `2026-10-29-*-fixed.json`；不为自己方便去写一个假的采集日期。
3. **非流式的改善不能归功于本次改动**。非流式端点本轮零改动，它从 100 并发 288/300 变成 300/300，
   主因是压测客户端把 `127.0.0.1` 从 `HTTP_PROXY` 里排除了（`7661d35`）。
   第一批那 12 个 500 是代理造成的，不是应用逻辑失败。
4. **压测数据里 `max_idle_in_txn_s = 0.459s` 高于冒烟的 23ms**。这是 100 并发下事件循环把
   「已开事务、SQL 已发」的任务押后所致，不是等外部调用；判据因此设为「有没有秒级空占」，
   且只有冒烟的 `checkedout()` 连续采样能区分两者。
5. **首帧 p50 变慢**（并发 100：0.77s → 1.19s），因为 `start` 帧现在要等前置块借到连接。
   与「整轮不再卡 32 秒」相比这个互换是划算的，但读表时不能说「全面变快」。
6. **TypeSafe 451 的白等没消掉**（未加熔断），`classify` 依旧是 TTFT 里最贵的自有环节，
   并行只是让 `memory` 被它遮蔽。要再压 TTFT 必须动它，另开规格。
7. **分段样本是靠补测具才拿到的**。`load_test.py` 起应用时用 `--log-level warning`，而 `本轮耗时`
   是 INFO —— 第一次收尾时 `stages`/`spans` 一条都没有，差点用「总量数据」冒充「分段验证」。
   已加 `--app-log-level info`，补跑 75 条样本（见 benchmarks 结果七）：两段外部依赖 span 之和
   p50 2608ms，实测 TTFT p50 1450ms，退回串行会是 2722ms —— 并行的收益是**用同一次运行内的
   算术**量出来的，不依赖跨批次对比。
8. **`memory` 有时比 `classify` 更慢**（75 条里 34 条）。所以 G4 的 1500ms 预算只是兜住长尾，
   它救不了均值：均值的钱只能靠并行省。
