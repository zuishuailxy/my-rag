# 文档目录

按**给谁看**分三类，与仓库根目录的三份门面文档分工明确。

```
docs/
├── architecture/   设计文档 —— 讲「这个系统为什么这么做」
├── benchmarks/     压测数据 —— 讲「实测出来是什么样」，含原始样本
└── interview/      面试材料 —— 讲「我为什么这么做，以及怎么证明」
```

## architecture/ —— 设计文档

面向**使用者和维护者**：想理解某个模块怎么设计的，从这里进。

| 文档 | 覆盖范围 |
| --- | --- |
| [`AgenticRAG流程.md`](architecture/AgenticRAG流程.md) | Agentic RAG 全链路：意图路由 → 工具循环 → 事件契约 → 前端对接 |
| [`长短期记忆.md`](architecture/长短期记忆.md) | 短期热窗口（Redis）+ 长期记忆（Mem0）+ 滚动摘要（Redis + PG双写） |
| [`文档可见性与写权限.md`](architecture/文档可见性与写权限.md) | 三层鉴权与可见性口径；权限码 vs 资源级判权的区别 |
| [`发布索引链路.md`](architecture/发布索引链路.md) | 发布后异步索引管线：一写三索引、幂等与失败重试 |
| [`上传解析模块.md`](architecture/上传解析模块.md) | 多格式解析（PDF/Word/PPT/Excel/图片）与资源托管 |
| [`文档模块CRUD.md`](architecture/文档模块CRUD.md) | 文档模块的数据模型与增删改查设计 |

## benchmarks/ —— 压测数据

面向**「这个数字是怎么来的」**：每次压测留一份原始 JSON（每请求耗时数组 + 环境元信息），
分位数随时可重算，不必重跑。

| 文件 | 内容 |
| --- | --- |
| [`benchmarks/README.md`](benchmarks/README.md) | 结果汇总：流式/非流式两套表格、TTFT 分段拆解、已知问题、与历史数据的关系 |
| `2026-10-29-stream.json` | 流式端点原始样本（5 档 × 3 轮，含 `ttft` / `first_frame` / `total` 数组） |
| `2026-10-29-chat.json` | 非流式端点原始样本（同环境对照） |

## interview/ —— 面试材料

面向**面试场景**：每条都写成能直接口述的形式，并附代码锚点与边界交代。

| 文档 | 内容 |
| --- | --- |
| [`面试实战问答集.md`](interview/面试实战问答集.md) | 21 题逐题应答，固定四段式：问题原话 → 口述答案 → 事实锚点（带文件:行号）→ 边界（如实交代） |
| [`面试应答稿.md`](interview/面试应答稿.md) | 重点项目问题的口述稿 + 追问预案 |
| [`面试题库-AgenticRAG.md`](interview/面试题库-AgenticRAG.md) | Agentic RAG 专项题库（原理 + 取舍 + 数字依据） |

> 这三份里的每个数字都会被 `backend/scripts/check_doc_numbers.py` 在 CI 里核对 ——
> 数字与源码 / 评测集算出来的不一致，PR 直接红。改文档里的数字前先改权威来源。

## 根目录的三份门面文档

| 文件 | 定位 |
| --- | --- |
| `README.md` | 门面：能力清单、效果数据、跑起来的步骤、CI 状态 |
| `项目导读.md` | 首屏入口：两条主链路图 + 功能↔代码对照表 + 逐文件职责 |
| `todo.md` | 内部待办与已完成清单 |

## 约定

- **文档里的行号会过期**。引用代码位置时优先写「函数名 + 文件路径」；写了行号的，
  改动相关代码后要回来核对（CI 只能核对数字，核对不了行号）。
- **数字只有一个权威来源**：评测集 jsonl / 源码本身 / 配置。文档只负责引用，不负责定义。
