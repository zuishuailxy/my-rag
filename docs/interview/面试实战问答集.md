## Q1. ES 中存了什么？为什么要存

### 问

ES 中存了什么？为什么要存。

### 答（口述）

ES 里存了两个索引。一个叫 `kh_document`，一条记录就是一整篇文档，存标题、摘要、正文、标签、作者、分类、发布时间这些，做的是搜索页的全文检索，用户打关键词能把文档搜出来，命中片段带高亮。另一个叫 `kh_chunk`，一条记录就是一个分块，存分块正文、所属章节标题、文档标题、块序号，还有权限相关的字段，这个是给 RAG 的关键词召回通道用的。

要特别说清楚一件事：**ES 里不存向量**。向量在 PostgreSQL 的 `doc_chunk` 表里，1024 维，用 pgvector 的 HNSW 索引做余弦近似检索。搜索里那条路和索引这边是彻底分开的：ES 那边只有倒排，PG 那边只有向量和元数据，没有冗余。

为什么还要留 ES，三个原因。

第一，**关键词精确召回是向量的固有盲区**。用户搜 `ERR_TIMEOUT_502`、搜 `antd`、搜某个具体报错码，embedding 会把它糊成一句语义相近的话，但 BM25 是按词项精确匹配的，能稳定命中。反过来问"文档更新之后旧的 chunk 怎么处理"，这种字面完全不重合的，只有向量能召回，BM25 抓不到。两边各有盲区，这才值得做混合检索——不是为了上新技术。

第二，**中文必须分词**，索引的时候用 `ik_max_word` 细粒度，查询的时候用 `ik_smart` 粗粒度。不挂分词器的话，一句中文在 ES 里就是一个 term，等于没做全文检索。

第三，**搜索页是我独立的一个功能**，不是 RAG 的附属品。它要返回带高亮的摘要片段，正文截 160 字、最多三段，标题整段不高亮——这是 ES 原生就有的能力，要放到 PG 里得自己写一套截取和标记拼装。

顺带说一下分工，这是我觉得比"存了什么"更重要的部分：**PG 是真值，ES 是派生索引**。向量那一路，权限过滤是直接 JOIN `kh_document` 主表现场查的，所以改权限立即生效、不用同步数据。ES 那一路没法 JOIN，只能在 chunk 上冗余一份权限字段，改权限的时候用 `update_by_query` 就地刷，不用重新分块也不用重新嵌入。同一个权限策略，两条链路两种实现，这个是刻意的，因为约束不一样。

最后是降级。ES 在整个系统里是旁路：写 bulk 失败就打个警告返回 False，不抛异常，向量照常落 PG；关键词召回那一路挂了返回空数组，退化成纯向量召回；查询向量化失败就只走关键词。所以 ES 整个挂掉，系统降级但不崩。

### 边界（如实交代）

- `kh_document` 用 camelCase、`kh_chunk` 用 snake_case——两个索引是分两次建的，命名风格没统一，不是笔误，但确实是该收的债。被问到就直说。
- `backend/eval/` 的实际构成我已核过：rag 148 条 = 120 单跳（oss 39 / travel 20 / release 15 / confusable 15 / shenlun 13 / resume 10 / attendance 8）+ 16 多跳 + 12 负例，另有 gen 58、graph 19 条。**可以报 148 这个数**，但不要说"225 条"。

### 如果被追问，一句话版本

- 为什么不把向量也放 ES？→ 迁 PG 是为了让向量和业务数据同库、事务一致、免跨系统双写，代价是多一套存储。
- 两个索引为什么不合并？→ 粒度和生命周期不同，重建 chunk 索引时会把文档级记录一起误删。
- `teamId` 为什么必须显式声明 keyword？→ 动态映射会建成 text，权限过滤用 `terms` 查会**静默失效**，不报错只是过滤不生效。这是我踩过的坑，所以补了幂等的 `put_mapping`。

## Q2. 先介绍一下你的这个项目

### 问

先介绍一下你的这个项目。

### 答（口述）

这是一个企业智能知识库系统，做的是把企业内部的文档——制度、流程、公告、FAQ——灌进去，之后让员工用自然语言提问，系统基于这些文档回答，并且每个答案都能溯源到具体是哪一段原文。

技术上是个 Agentic RAG 的完整链路，后端 Python 加 FastAPI 全异步。存储用了五套：PostgreSQL 存元数据和向量、Elasticsearch 存倒排索引、Neo4j 存知识图谱、MongoDB 存文档正文、Redis 管热窗口和限流，RabbitMQ 跑异步管线，Docker Compose 一条命令起全套。

整个系统就两条主链路，我按这个讲。

**写入链路**：上传文件，先解析成统一的 Markdown，PDF、Word、PPT、Excel、文本各有解析器，图片走视觉模型做 OCR。然后分块，块大小 512、重叠 64，块 ID 是 sha256(文档ID:序号) 算出来的确定性 ID——这点很重要，意味着重建索引能幂等 upsert，不会产生重复数据。最后**一写三索引**：向量进 PG，全文进 ES 的文档级和块级两个索引，实体关系进 Neo4j 图谱。这一步是异步的，发布完往 RabbitMQ 投消息，消费者去做，不阻塞用户上传。

**问答链路**，这是我认为跟普通 RAG 区别最大的地方：**检索不是一个固定的预处理步骤，而是 Agent 手里的一个工具**。用户提问先过意图路由，分成五类，决定给 Agent 挂哪些工具——知识库检索、查询改写、图谱检索、联网搜索。Agent 是 LangChain 的 create_agent，自主决定调哪个工具、调几次。检索到的东西还要过一道切题判定，如果发现召回的内容跟问题不相关，可以改写查询重试一次，然后才拿去生成答案。答案走 SSE 流式下发，思考过程、工具调用、引用编号都是流里带的。

检索这块是最需要打磨的地方，我做了四层：ES 关键词和 PG 向量两路并行召回，RRF 融合成候选，再交给 cross-encoder reranker 精排，最后按相关性阈值过滤。**四层消融的效果是可测的**：难例上纯关键词 hit@1 是 0.706，加向量召回涨到 0.804，加兜底门控 0.824，最后加 rerank 到 0.941。这是 148 条评测集跑出来的，不是拍脑袋。

还有个数字我比较在意：压测 100 并发零失败，而且这不是靠调大连接池做到的——同池 15 的情况下修复前并发 20 就有 5 个失败，修复后 100 并发全过。根因是 FastAPI 的生成器依赖把数据库连接占着等 LLM 响应，池子是被"占住"而不是"不够用"，所以调池子大小治不了本。

对检索质量影响最大的一课是：**兜底门控这个设计在组合故障下会把召回归零**。单个组件挂了我都有降级路径，但两个一起挂、或者挂在特定组合上的时候，多个降级分支叠加，反而把所有候选都过滤掉了，最后返回空。这个是评测跑出来的，不是线上用户投诉出来的。

**边界我先说清楚**：这是我个人项目，没有真实企业用户和真实流量，174 篇语料是我从公开仓库抓的 MIT 授权文档，评测集也是我自己标的。系统能不能扛住真实生产环境的并发和数据量，我没有证据，只能说架构上考虑了降级和幂等。

## Q3. ES 里存的文档和 MongoDB 里的有什么区别

### 问

ES 里面存的文档和 MongoDB 里面的区别是什么？

### 答（口述）

先说结论：**MongoDB 是正文的真值，ES 里那篇文档是从它派生出来的搜索副本**。同一份 Markdown 正文存了两份，但定位完全不一样。

Mongo 那边是 `document_content` 集合，一条记录对应一篇文档的完整正文，`_id` 是 ObjectId，PG 的 `kh_document.content_id` 就指向它。除了正文还有正文字符数、摘要预览、版本号、逻辑删除标记。它的访问模式是**按 ID 精确取**——文档详情页要显示全文、审核时要预览正文，都是 `find_one` 拿一整篇回来。

ES 那边是 `kh_document` 索引，同样的文档作为一条记录，但里面多了标题、作者、分类、标签、发布时间、浏览数点赞数这些元数据，正文也在里面，但它不是为了"读全文"存在的，是为了让**搜索能命中**。字段名是 camelCase，跟前端契约对齐。它的访问模式是**全文检索**——用户打关键词，ES 分词打分返回 topN，而且返回的时候 source 里明确 excludes 掉 content，说明列表页根本不回传全文，只要高亮片段。

所以同一个字段 `content`，两边都有，但语义不同：Mongo 那边是**数据**，ES 那边是**索引材料**。Mongo 是 SSOT，ES 丢了可以重建，我有个 reindex 脚本能从 PG 加 Mongo 全量重建；ES 删了不影响任何业务功能。

有个细节值得说：写入的时候 MQ 消息**只带文档 ID，不带正文快照**，消费者收到 ID 之后自己去 PG 拉元数据、去 Mongo 拉正文，拼成一份统一快照再写 ES。这样消息体很小，重试的时候不会带着一大坨正文在队列里跑。

**为什么正文要进 ES 而不是只在 Mongo？** 因为搜索页要的是"命中正文里的哪一段"，这是 ES 的原生能力。放 PG 全文检索要自己造分词和排序，放 Mongo 全文索引能力更弱。而且 Mongo 的文档是按 ID 取的，让它承担"关键词模糊命中"不划算。

一句话总结：**Mongo 管"读到这篇文档"，ES 管"搜到这篇文档"，PG 管"这篇文档是什么"。**

### 如果被追问，一句话版本

- **为什么不直接把 ES 当正存储？**→ ES 是倒排索引不是文档库，没有事务、没有约束、误删难恢复；它设计上就只做检索层。
- **两边数据不一致了怎么办？**→ 以 PG + Mongo 为准，ES 可全量重建；reindex 脚本就是干这个的。
- **Mongo 存全文，PG 不是也有 content 相关的吗？**→ PG 是`kh_document`，只有 `summary`、`word_count` 这类元数据和 `content_id` 指针，没有正文列，正文只在 Mongo。
- **为什么 ES 字段名和 Mongo 不一样？**→ ES mapping 对齐前端契约用 camelCase，Mongo 是后端内部模型用 serialization_alias 转驼峰，两边各有约束。

## Q4. 你是怎么用判别模式的？它起什么作用？为什么这么设计？

### 问

你是怎么用判别模式的？它起什么作用？为什么这么设计？

### 答（口述）

先说清楚我说的"判别模式"是什么：我在检索链路上用了 **TypeSafe 这个判定式服务**，它跟生成式 LLM 是两套完全不同的协议——生成式 LLM 是 OpenAI 兼容接口、靠 messages 生成文本；TypeSafe 是结构化判定，调用是 `system_one`，传进去一个状态和若干问题，拿回来的是**类型化的分类结果**，不是文本。它有三个原语，Noul、Choice、Score，我全项目只用了 Choice，因为另外两个我不需要。

**我用了三处判别，都是"分类"而不是"生成"**：

第一处是**意图路由**，五选一：闲聊、个人偏好、查知识库、联网搜、知识库不够再联网搜。这个结果直接决定给 Agent 挂哪些工具——挂知识库检索、还是挂联网搜索、还是都不挂、只处理闲聊。


第二处是**改写门控**，三选一：问题自足、依赖上文、不需要检索。这次的价值最大，因为它**省掉了大部分 LLM 调用**——只有判定为"依赖上文"的那轮才真的去调 LLM 做指代消解。像"今天天气怎么样"这种自足问题，判定完直接跳过改写；像"那谁审批""这个怎么办"这种追问，才值得花一次 LLM 把指代补全成独立可检索的短查询。

第三处是**切题判定**，两选一：切题、不切题。检索回来的块跟问题是不是一个主题，这条决定要不要触发改写重试，也决定知识库没命中时要不要转联网搜。

**为什么这么设计**，我有三个考虑。

第一，**判别和生成是两种任务，不该用一种模型干**。分类任务的输出空间是封闭的——五选一就是五选一，我不需要模型"创作"什么。而生成式 LLM 做分类有已知问题：要解析 JSON、要处理格式跑偏、要防它给你编一个不存在的标签。我代码里专门做了这层防御，模型返回的意图如果不在枚举里，我当它不可用，走回退。判别式返回的是**类型化结果，天然受约束**。

第二，**成本和延迟**。判定式调用比生成式便宜快，尤其是改写门控那一处——把它前置，等于给 LLM 调用加了一道筛子，把不需要 LLM 的轮次全部挡掉。

第三，**它跟主 LLM 解耦**。TypeSafe 是独立 SDK、独立的 Key，我用延迟导入，没装或者没配 Key 就返回 None，**所有判别点统一回退 LLM**，不影响模块加载。回退是分级的：判别不可用先用 LLM 的 `need_retrieve` 推意图，推不出来落到知识库；切题判定两路都不可用返回 None，调用方按切题处理——**判定是增强环节，任何故障都不能让用户问不出结果**。

还有个细节值得说：判别结果里带 `confidence` 和各选项的 `probabilities`，我记进日志了。切题判定那里还把 confidence 写进 reason 字段，方便观测"这次判定把握多大"。

## Q5. 讲一下权限过滤是怎么做的

### 问

讲一下权限过滤是怎么做的。

### 答（口述）

可见性模型很简单，三条并列，**命中任一即可读**：公开的、自己写的、所在团队的。管理员和审核员视为不受限，不加任何过滤。

关键是**这个判定要在三条检索链路上分别落地**，因为每条链路的技术形态不一样。

**ES 侧**用 filter 子句：`bool.should` 里放三个条件——`is_public = true`、`author_id = 当前用户`、`team_id in 我的团队列表`，配 `minimum_should_match: 1`，也就是三者命中任一就可读。两个索引字段名不一样，`kh_chunk` 是 snake_case、`kh_document` 是 camelCase，我用同一份实现传不同的字段映射表。**这里有个细节：可见性子句放 filter 上下文，不放 must。** 因为 filter 是只筛不参与打分的，如果放 must 里，权限条件会参与 BM25 计算，用户的团队背景就会影响结果排序——这显然不对。

**PG 向量侧**用 SQL 的 JOIN：查向量的时候 JOIN `kh_document` 主表，在 WHERE 里判同样的三个条件。我这里**故意不在 `doc_chunk` 表里冗余 `is_public`**，因为向量路能 JOIN 主表，改权限立刻生效、不需要同步数据。ES 那边没法 JOIN 才冗余一份，改权限时用 `update_by_query` 就地刷。同一个权限策略、两种实现，原因是约束不同。

**Neo4j 侧**在 Cypher 里拼条件，四个查询方法逐条都带可见性子句，口径跟 ES 侧完全一致。

还有**几个必须防的坑**，这几个是我认为权限设计里最容易出事的地方：

第一，**兜底方向必须是保守的**。无登录用户或者 scope 缺失时，我用 `empty_scope()` 兜底，语义是"只能看公开内容"——`user_id` 是空字符串，永远匹配不到任何作者，`team_ids` 是空列表。**绝不能兜底成"不过滤"**，否则就是全站泄露。

第二，**读权和写权是两套规则，不能混**。读侧管理员和审核员都不受限，但写侧**只有管理员和作者本人**——审核员不算。因为审核员是通过审核接口处置别人的文档，他不需要、也不应该拿到通用改写权。这里有个实现细节：判定写权要的是 `AuthUser` 而不是 `DocumentAccessScope`，因为 scope 里的 `unrestricted` 是管理员和审核员**合并后的标志位**，分辨不出具体是谁。

第三，**权限码不能替代资源级判权**。`require_permission("document:edit")` 只能回答"能不能用这类接口"，回答不了"能不能动**这一篇**"。缺了后一层校验，任何持有 edit 权限的角色都能改删别人的文档——我的种子数据里普通角色就同时持有 edit 和 delete，所以这层是必需的。

第四，**字段类型必须是 keyword**。权限字段如果被 ES 动态映射建成 text，查询走的是分词后的词项匹配，跟 `terms` 的精确匹配语义不同，会让权限过滤**静默失效**——不报错，只是过滤不生效。这种 bug 靠测功能是测不出来的。

### 事实锚点

| ---------------------------------------- | ------------------------------------------------------------------------- |

- `neo4j_access_params(scope=None)` 返回 `unrestricted=True`，也就是**不传 scope 等于不过滤**。生产链路必须传 `access_from_user(user)`，我四个图谱端点都传了，但这是一个"默认放开"的危险默认值。

### 如果被追问，一句话版本

- **过滤放应用层还是查询层？**→ 查询层。应用层过滤等于先取全量再筛，既泄露风险又没法分页。
- **性能影响？**→ filter 上下文不参与打分，ES 侧还有缓存；PG 侧是 JOIN 主表，主表有主键索引，代价可接受。但**权限条件进不了 HNSW 的索引查找**，只能在结果集上过滤——这是 pgvector 方案的固有短板。
- **怎么测权限？**→ 关键是不能只测"有权限能看见"，更得测"无权限看不见"。ES 侧还要专门测字段类型是否 keyword。
- **管理员要不要也过滤？**→ 不用，unrestricted 短路返回 None（不加 filter），这是刻意设计。

## Q6. RBAC 是什么？RBAC 和权限系统是怎么结合的？

### 问

RBAC 是什么？它和权限系统是怎么结合的？

### 答（口述）

RBAC 是基于角色的访问控制。核心是**不让权限直接绑到用户身上，而是绑到角色，用户通过担任角色来获得权限**。这样"能改文档"这个权限只需要在角色上配一次，分配给谁由角色成员关系决定；人员变动时改的是角色关联，不是逐个用户授权。

标准模型是四个要素：**用户、角色、权限、以及三者的两张关联表**（用户-角色、角色-权限）。我这套就是照这个建的，`kh_user`、`kh_role`、`kh_permission` 三个实体，加 `kh_user_role` 和 `kh_role_permission` 两张关联表，权限本身是**树形结构**的，靠 `parent_id` 表达"文档管理 → 文档编辑"这种层级。

**和权限系统的结合，我分两个原语：`roles` 和 `require_permission`。**

`roles` 是粗粒度的，按角色码判——是不是管理员、是不是审核员。`require_permission("document:edit")` 是细粒度的，按权限码判，**拥有的权限码里命中任意一个就放行**。用法上两者是组合的，要管理接口就 `@roles(ADMIN)` 加 `require_permission("system:role")`。

**关于管理员我有个明确的设计：不做硬编码 bypass。** `require_permission` 这个守卫里**没有**"如果是管理员就放行"的捷径，而是通过 `get_user_permission_codes` 把管理员身份**翻译成具体权限码**——用户拥有任一管理员角色时，就自动追加一份管理员操作权限码清单，比如 `document:edit`、`system:user` 这些，一共 18 个。这样做的好处是**判权逻辑只有一条路径**，管理员和普通用户走同一套判断，不存在"管理员走特权分支、普通用户走正常分支"这种双轨，也就不会出现两条分支判断不一致的 bug。而且这个追加是基于**角色码**的，不是硬编码用户 ID，所以以后加一个新管理员角色，只要把角色码加进 `ADMIN_ROLES` 元组就行。

**鉴权的位置我选了自定义路由类而不是中间件**，这是我在这个项目里比较满意的一个决定。原因是中间件运行在**路由匹配之前**，那一刻拿不到 endpoint 上打的标记，只能退化成硬编码路径白名单——白名单和路由定义分散在两个文件里，新增公开路由忘了同步，接口就被自己的守卫拦成 401，而且从路由文件里看不出任何异常。自定义路由类 `AuthRoute` 是唯一能在"路由匹配之后、依赖解析之前"读到 endpoint 元数据的扩展点。同理，**默认行为是"未标记就一律需要登录"**，忘记标记等于被保护；反过来默认公开、逐个标记要登录，漏一个就是永久漏洞。这个方向的选择是 fail-safe。

权限码最终怎么落到数据上，还有一环是**数据可见性**。我登录和每次鉴权都会把用户的角色码、合并后的权限码、所在团队 ID 一起组装成一个 `AuthUser`，检索侧拿这个对象算出可见范围——公开 ∪ 本人 ∪ 所在团队。所以 RBAC 管的"能不能调这个接口"和可见性管的"能看见哪些数据"是两层，前者管功能入口，后者管数据范围，**权限码替代不了资源级判权**：一个人有 `document:edit` 也不意味着他能改任何一篇文档，还得判是不是他自己写的。

- 权限查询每次请求都打一次库，**没有缓存**。鉴权结果和用户绑定，用户权限变更需要立即生效，所以没做缓存；如果要加，得接受"权限变更有延迟窗口"。

- 团队是**独立于 RBAC 的第四个维度**，团队树有 `parent_id`，但**成员只有叶子节点，没有"父团队成员自动可见子团队文档"的语义**。

### 如果被追问，一句话版本

- **RBAC 和数据权限（ABAC）什么关系？**→ 我这套是 RBAC 管功能入口 + 简化的 ABAC 管数据范围（用"公开/本人/团队"三个属性判定），两条链路共用同一个 `AuthUser`。
- **为什么不用 ACL（直接给用户挂权限）？**→ 挂是可以的，我的 `get_user_permission_codes` 就同时合并了直接权限和角色权限。但纯 ACL 人员变动要逐个改，运维成本高，所以以 RBAC 为主、ACL 为补充。
- **权限码和角色名要不要一一对应？**→ 不要，角色是"人"的抽象（管理员、审核员），权限码是"操作"的抽象（`document:edit`）。一个角色对应多个权限码，这是 RBAC 的核心价值。
- **管理员权限清单硬编码在代码里，灵活吗？**→ 不灵活，18 个码在 `common/permissions.py` 里，加操作要改代码。更合理的是在 `kh_role_permission` 表里给管理员角色配全量权限，但那样就得处理"这个角色是不是管理员"的特殊逻辑，我又不想在守卫里开 bypass 分支——这是我选的一个折中，不算最优。

## Q7. 权限码是什么？前端是做权限的？

### 问

权限码是什么？前端是做权限的？

### 答（口述）

权限码就是一个**字符串标识**，用来命名"某个具体操作"，比如 `document:edit`、`document:delete`、`system:user`。它存在 `kh_permission` 表里，一条权限码记录还带名称、类型（1 菜单 / 2 按钮 / 3 接口）、菜单 URL、图标、排序。

命名规范是**冒号分层**：`模块:操作`，树形结构的层级和冒号层级是对应的——`document` 是菜单节点（指向 `/documents`），下面是 `document:list`、`document:create`、`document:edit` 这些按钮节点；`system` 是菜单（指向 `/admin`），下面是 `system:user`、`system:role`，再往下还有 `system:permission:create` 这种三层的。所以**权限码本身自带层级信息**，不需要额外维护"权限属于哪个模块"。

关于前端做不做权限——**做，但只是体验层，真正的拦截在后端**。这个区分很关键，我说说具体怎么落的。

前端拿到的登录响应里就有 `permissions: string[]`，是一个权限码数组。然后有三个地方消费它：

第一是**菜单和按钮的显隐**。侧边栏根据 `document:list`、`search`、`profile` 这些码决定显示哪些入口；文档列表页只有 `document:create` 才显示"新建"按钮；详情页的编辑、删除按钮也是按码显隐。

第二是**路由守卫**。我封装了个 `<Perm code="...">` 组件包路由，用户没这个码就重定向到首页。

第三是**资源级判断**。这个跟前两层不一样：`document:edit` 只说明"能编辑文档"这个操作，但能不能编辑**这一篇**，还得看是不是自己写的，所以我有个 `canWriteDocument(user, doc)`，判 `isAdmin` 或者 `doc.authorId === user.userId`。列表页的编辑按钮就是 `can(user, "document:edit") && canWriteDocument(user, row)` 两个条件同时成立才显示。

**为什么必须后端也拦一遍？** 前端这些判断全在浏览器里，用户改一下 JS 就能绕过。所以后端每一个写接口都挂了 `require_permission` 依赖，**前端的 `can()` 只是"不让用户看到点不动的按钮"，后端的守卫才是"点了也没用"**。这两层缺一不可：只有后端拦，用户体验差，会看到点了报错的按钮；只有前端拦，等于没拦。

顺带说一个我特意处理的地方：前端 `can()` 里我写了 `if (user.roles.includes("ROLE_ADMIN")) return true`——**管理员在前端直接放行所有码**。但后端 `require_permission` 里**没有**这个捷径，它是通过把管理员身份翻译成 18 个具体权限码来放行的。两边看起来不一致，其实是刻意的：后端那条路径我要保持单一判权逻辑、不开特权分支；前端这样写只是省事，而且后端会兜住，真出了差异也漏不出去。

### 事实锚点

| 结论 | 位置 |
|---|---|
| 权限码表结构（code/name/type/menu_url/icon） | `init-scripts/postgresql/init.sql`：`kh_permission`（约 131-140 行） |

### 边界（如实交代）

- **`PermissionType` 定义了 3 种类型（菜单/按钮/接口），但种子数据里实际只用了 1 和 2，没有 type=3 的接口权限**。后端守卫不区分类型——`require_permission` 只看码存不存在，不看它是什么类型。所以"接口权限"这一层目前是名义上的，没落地。
- 前端 `can()` 的管理员放行是**硬编码 ROLE_ADMIN 字符串**，没有走统一常量（后端有 `RoleCode` 枚举，前端没有对应物）。改角色码的话前端要同步改。
- 前端权限判断**只做了显隐和跳转，没有做禁用态**。比如没有权限的按钮是直接消失，不是灰掉不可点。这是刻意的简化——从 UX 上，不给用户"点了没反应"的期待。
- 权限树是**两级半**：最深到 `system:permission:create` 这种三层，没有更深的了。树的深度目前是数据决定的，不是代码限制。

### 如果被追问，一句话版本

- **权限码和角色名怎么对应？**→ 多对多，靠 `kh_role_permission`。一个角色多个码，一个码也能给多个角色。
- **权限码是不是硬编码在后端的？**→ 不全是。18 个管理员码硬编码在 `common/permissions.py`，但 `kh_permission` 表里的码是数据、可以增删，`require_permission` 传的码是路由上写死的字符串常量。新增权限要同时改表和路由，但**不需要改权限服务的代码**。
- **前端藏了按钮，后端还会拦吗？**→ 会，这是设计意图。前端是 UX，后端是安全边界。
- **为什么不用 JWT 里带权限？**→ 考虑过，权限变更要立刻生效。JWT 是签发时固化的，改权限得等 token 过期，用户体验差，而且没有主动失效机制。所以每次请求查一次库。

## Q8. 讲一下你后端如何自己实现 SSE

### 问

讲一下你后端如何自己实现 SSE。

### 答（口述）

先说清楚背景：前端用的是 Vercel AI SDK 的 `useChat`，它对后端协议有要求——必须发 **UI Message Stream** 格式的 SSE，也就是带 `text-start` / `text-delta` / `text-end` 这种**成对事件**的协议，不是普通 SSE 那种只发 `data:` 的消息流。

**为什么自己实现而不找现成的库？** 我评估过几个：要么要求的 FastAPI 版本太高，要么会丢掉 reasoning（思考过程）的透传，要么不支持 `data-*` 自定义帧和流合并。所以我写了个 `UiMessageStreamWriter` 类，大概两百行，核心就是把"自动开合"这件事做对。

**SSE 本身很简单**，就是 `data: {json}\n\n` 这个格式，一个静态方法 `write()` 拼字符串。难的不是 SSE，是**协议状态机**。

我的编码器维护三个状态：正文 part 的 id、思考 part 的 id、以及工具输入已发过的集合。规则是：**首个 delta 到达时才发 start**。比如正文，用户不是一上来就收到 `text-start`，而是模型吐出第一个 token 时才发 `text-start` + `text-delta`；后面再有 token 就只发 `delta`；流结束时补 `text-end`。这样 start 和 end 永远配对，不会出现有 start 没 end 的悬挂 part。

**最容易踩的坑是 part 嵌套**。模型可能先输出一段思考、再输出正文。我的处理是：正文开始前，如果思考 part 还开着，**先补一个 `reasoning-end` 把它收口**，再发 `text-start`。这样两个 part 严格顺序、不交叉。工具调用也是同理，用 `_tool_input_started` 和 `_tool_input_sent` 两个集合去重——因为模型的流式输出里，`tool_call_chunks` 和 `tool_calls` 可能对同一个调用发两次，得保证 start 和 available 各只发一次。

**Agent 的流我用三个 stream_mode 订阅**：`messages` 拿模型的 token 和思考、`updates` 拿工具结果、`custom` 拿工具内部推的事件。这三个走一条 `async for` 同时消费。

这里有个我觉得比较巧的用法：**工具内部也能往流里推帧**。我用 LangGraph 的 `get_stream_writer()`，在 `retrieve_knowledge` 执行过程中直接推 `data-eval`（切题判定结果）、`data-sources`（命中来源）、`data-status`（"正在改写检索词"这类过程状态），前端的过程条就是靠这些实时更新的。**这意味着工具执行中和模型生成中是同一条流，用户不用等回答结束就能看到检索进展。**

然后是引用溯源。我让模型在回答里写 `[n]` 编号，流结束后用正则把实际用到的编号提出来，**只把这几条来源落库**——模型检索了 10 条但只引用了 2 条，数据库里就只存那 2 条，不存 10 条。

**还有两个工程细节必须提**：

一个是**内部 LLM 调用要过滤**。工具里的改写、切题判定也会调 LLM，这些 token 如果直接进 messages 流，会变成回答正文里突然冒出来的 JSON。我在内部调用上打了 `kh-internal` tag 并清空 callbacks，消费流时按 tag 过滤掉。

另一个是**配额要在推流前校验**。超限直接返回 429，而不是先 200 再在 SSE 里推一个 error 帧——因为那时候响应头已经发出去了，状态码改不了。

### 事实锚点

| 结论 | 位置 |

### 边界（如实交代）

- **反压（backpressure）没做**。我用的是 FastAPI `StreamingResponse` 包一个异步生成器，消费者慢时我这边没有显式的流控手段，靠 ASGI 层的缓冲和 TCP 窗口自然兜。这在长回答 + 慢客户端的场景下理论上会占用内存。
- **`data-*` 自定义帧的语义是 AI SDK v6 协议约定的**，我按 v6 写。前端 SDK 升级大版本时，这层可能要跟着动。
- **异常时只发 `finish` + `[DONE]`，不发 error 帧**。中途失败的话，前端会看到一个"正常结束但内容不完整"的回答，没有明确的错误提示。生成器里`except` 只记日志这是我有意简化——**SSE 一旦开始推就没法改状态码**，把错误编码进流里需要前端配合识别，我还没做。
- **没用 `sse-starlette`**。手写生成器的好处是能精确控制 part 状态机，代价是没有自动心跳（heartbeat）——如果中间有长时间静默（比如 rerank 耗时），代理层可能因为超时断连。我这边靠 rerank 通常在秒级，加上前端有重试，实践中没遇到问题，但这是**没根治的隐患**。
- 工具推的 `data-sources` 每次是**全量快照**（前端覆盖），不是增量。这是刻意简化，代价是多次检索时会有重复传输。

### 如果被追问，一句话版本

- **为什么不用 `EventSourceResponse`？**→ 那是标准 SSE 消息流，AI SDK 要的是带 part 状态机的 UI Message Stream，两者格式不同。而且我要控制 part 开合与去重，包一层反而更绕。
- **怎么保证 start/end 配对？**→ 不靠事后校验，靠"首 delta 才 start"这个规则从源头保证；流结束统一补 end，异常路径也有 finally 兜底。
- **为什么工具里能推流？**→ LangGraph 的 custom stream mode 就是给这个用的，`get_stream_writer()` 在图内拿到写端，在图外会抛异常所以我退化成 no-op（冒烟测试直接 invoke 工具时不报错）。
- **中间要加心跳吗？**→ 该加，这是我的隐患。目前靠 rerank 秒级返回 + 前端重试绕过去了，生产环境应该补。

## Q9. 你是如何设计记忆系统的

### 问

你是如何设计记忆系统的？

### 答（口述）

我先用一个类比：**记忆对我来说就是三层不同粒度的抽屉**。

第一层是**最近的话**（短期记忆，Redis 热窗口）。就像你跟人聊天，默认只记得最近几句。存最近 20 条问答原文，key 是 `kh:chat:{用户id}:{会话id}:messages`，过期时间 24 小时。这里只放用户说的话和 AI 说的话，一字不改——**逐字保真**，因为最近这几轮往往是"那报销单要交哪个部门？"这种必须一字不差地接上的话。

第二层是**更早的话**（滚动摘要）。窗口只有 20 条，聊到第 25 轮的时候，第 1~5 轮就被挤出去了。但那一轮里可能说了"我是 EMP-7788，工号"。我不能让这些信息消失，所以就把滑出窗口的旧对话**压缩成一段话**，压到 400 字以内，作答时当成背景塞给 AI。压的过程是增量的：每次只压新滑出去那几条，然后跟老摘要重新合成一段，不会重复读全文。存两处：Redis 一份（快），PostgreSQL 一份（Redis 挂了还能兜底），跟短期记忆同一套"Redis 优先、数据库兜底"的写法。

第三层是**跨会话的长期记忆**（Mem0 托管平台）。前两层都只管当前这个会话，用户开个新会话就全没了。但"我是张三，做财务的"这种信息应该跨会话记住，所以我接了 Mem0。它有两层：user 层（跟着用户走，跨所有会话）和 session 层（只管这个会话）。每层检索各取 5 条。

**为什么要分这么细？因为它们保真度不一样、失效代价不一样。** 最近的话要一字不差，所以存原文；旧对话只要"大致记得说过什么"，所以可以压；跨会话的偏好最抽象，所以让平台去抽取事实，我只负责拼提示。

几个我觉得比较关键的设计取舍：

**第一，记忆只作背景，不能当制度依据。** 每条拼给 AI 的记忆后面都跟一句硬话："以上仅作背景，制度/流程以本轮检索资料为准，不要用记忆替代文档。" 因为记忆是会出错的——用户上个月说他下周出差，这句话到下个月就是错的。如果允许模型拿记忆当事实回答，那错的就是答案本身。所以我把它设计成"背景提示"，制度原文永远只从知识库检索来。

**第二，任何一层记忆坏了都不能影响对话。** Redis 挂了 → 短期记忆返回"没命中"，改查数据库。Mem0 没配 key 或者超时 → 返回空，AI 照样能回答。摘要模型报错 → 只记警告。**记忆是增强项，不是依赖项。**

**第三，读回来的东西要过滤。** 记忆里除了用户的原话，还有我的思考过程、检索到的资料原文、系统提示。这三类都不能进历史窗口——它们是一次性的，下一轮留着只会干扰模型。所以我有一个统一的判定函数：只有用户消息和 AI 回答算数。**Redis 读出来的和数据库查出来的走同一个判定**，否则从库里回填一次就会把检索资料灌进窗口。

**第四，一轮对话结束后的写回分两种等待方式。** 短期记忆是同步写的（很快，就是写个 Redis）；长期记忆和滚动摘要都是**丢到后台跑**，不等它们。为什么？因为长期记忆要先调一次分类器判断"这条该写用户层还是会话层"，那是额外一次 LLM 调用，秒级；摘要也要调模型。**让用户等这些纯属浪费。**

最后补一个我觉得挺有意思的坑：我一开始想用 LangChain 自带的摘要中间件，后来删了。因为那个中间件只看得见已经进 agent 的那 20 条，而且摘要只存在 agent 的内存状态里不落盘，**每轮都要从 20 条重新算一遍**——它压不到窗口之外的历史，等于白做。所以我自己做了滚动摘要：跨请求持久化，只压新滑出去的部分。

### 边界（如实交代）

- **只接了流式问答。** `services/ai_chat.py`（非流式那条链路）**还没接**这四层记忆，只有 `ai_stream` 接了。这是已知缺口，不是我打算藏着的——非流式接口目前是"每次调用都无记忆"的。
- **滚动摘要的锁是进程内的** `asyncio.Lock`（`chat_summary.py:127`），多 worker 部署时同一会话的折叠需要换 Redis 分布式锁。而且这个字典只增不减，会话数多了是个慢泄漏。
- **摘要的水位依赖"雪花 id 在单进程内严格递增"**，而 `machine_id` 是硬编码的 1。多进程既不保证 id 唯一也不保证全局有序，所以多 worker 下折叠水位可能算错。
- **长期记忆的「抽取」不在我这边。** Mem0 是托管平台，`add()` 由云侧抽取事实，**SDK 不暴露模型参数**，只能用 `custom_instructions` 约束输出。我进程里只有分类器（判"写用户层还是会话层"）走 deepseek。要让抽取也走自有模型，得改成 Mem0 OSS 自托管。
- **`delete_all(user_id, run_id)` 会忽略 run_id、清空该用户全部长期记忆**（实测：4/1/1 → 0/0/0）。所以删会话不能直接用它，我改成先 `get_all` 列 id 再逐条 `delete`。顺带一提，TS 那边的 `deleteAll({userId, runId})` 做同一件事，是同样受害的。
- **Mem0 的写入是异步的**，返回 `status=PENDING`，实测 6~9 秒后才检索得到。所以"本轮写进去、本轮立刻读回来"这种设计不成立，冒烟测试必须轮询等待。
- **记忆没有过期策略、没有增删改查接口、没有按 team 维度隔离**，也没做分类器判定的落库审计。跨会话长期记忆目前只有 user / session 两层 keyed by id，团队维度的共享记忆我没做。
- **短期记忆写入失败会静默退化。** 如果消息里塞了不可 JSON 序列化的对象（比如 `response_metadata` 里塞了 datetime），每轮都写失败 → 每轮都 miss → 每次都回落查库。功能是对的，但缓存变成空转，而且日志里只有一条 WARN，不主动查看不出来。

### 如果被追问，一句话版本

- **为什么分三层？**→ 保真度和失效代价不一样：最近的话要一字不差（存原文），旧对话可以压（存摘要），跨会话的偏好最抽象（让平台抽事实）。
- **为什么不全部交给向量数据库？**→ 记忆和知识库是两种东西。知识库是"制度怎么规定的"，要能被检索到、能溯源；记忆是"这个人是谁、他在做什么"，是背景。而且记忆会过时，所以我在提示里明确写了"制度以本轮检索为准，不要用记忆替代文档"。
- **Redis 挂了会怎样？**→ 短期记忆 miss，改查数据库，功能不受影响。长期记忆失败返回空。所有记忆层的失败模式都是"降级 + 记日志"，不阻断对话。
- **为什么短期记忆只存原文不存摘要？**→ 最近这几轮通常是"那报销单交哪个部门"这种依赖原话语义的追问，改写一次就可能接不上。
- **摘要为什么存两个地方？**→ Redis 快但会没，PostgreSQL 稳但慢一层。这套"Redis 优先、数据库兜底"的写法我用了第三次（会话摘要、短期记忆都是这个模式），是刻意统一的。
- **旧对话压成摘要会丢信息吗？**→ 会。所以我只压"已经滑出窗口"的部分——那些对话 AI 本来就看不到了，压成 400 字比直接丢掉强。而且下一轮新增的内容仍然进窗口保持原文。
- **长期记忆为什么用托管平台而不是自己写？**→ 抽取事实这件事自己写要处理去重、冲突消解、时效判断。托管平台的代价是我控制不了抽取用的模型，这个代价我认了——所以我才在提示里加免责句，把记忆的作用限制在"背景"。
- **后台任务失败了怎么办？**→ 吞掉只记警告。长期记忆和摘要都是"增强"，丢了不影响这一轮回答，下一轮会因为没有相关记忆而少一点上下文，不影响正确性。

## Q10. 判断是否需要写入 Mem0，现在用什么方法？能不能用判别式替换？

### 问

判断是不是需要写入 Mem0，现在是用什么方法判断的？是不是可以用判别模式（TypeSafe）来替代？

### 答（口述）

**现在的判定是生成式 LLM 做结构化分类。** 每轮问答结束、调Mem0 写入之前，我先跑一个"记忆分类器"——用 `with_structured_output` 让 LLM 吐一个结构化对象出来，三个字段：`write_user`（要不要写跨会话的用户层记忆）、`write_session`（要不要写当前会话层记忆）、`reason`（分类理由）。温度固定 0 保证可复现。模型走的是 deepseek-v4-flash，`function_calling` 模式、关掉 thinking。

提示词里我把边界写得很死，主要是四类**不写**：寒暄致谢、**助手根据检索资料说出的制度和流程**、联网搜索结果和引用编号、无信息增量的复述。还有一条原则最重要：**知识库内容永远不能写成 user 记忆**——制度条文是文档事实，不是用户记忆。还有一条容易搞错的：「这次先看差旅制度第三节」这种带"这次"的应该标 session，不是 user。

**还有个关键设计：只把用户说的话交给 Mem0 抽取。** `extractFrom` 里只有 question，助手回答只是给分类器判断上下文用的、不参与抽取。这样即使模型抽取跑飞了，也不会把制度条文写进长期记忆——抽取侧还有 `custom_instructions` 再兜一道。

**能不能换成 TypeSafe？** 我认为**这个场景比现有的三个判别点更适合用判别式**，理由有三条：

第一，**这本来就是分类任务，输出空间封闭**。现在返回的是三个字段，但真正的判断只有四种组合——都不写、只写 user、只写 session、两个都写。这是典型的有限枚举，判别式天生擅长。而且 `reason` 字段本质是日志信息，不是决策输入，**换成判别式还能顺手砍掉这个字段的 token 成本**。

第二，**同进程里已经有一个完全同构的先例**。意图路由决定"要不要联网搜索"，是 TypeSafe 的五路 Choice；而"要不要写记忆"是四路组合。两者在同一轮对话里、在同一个 `chat_query_rewrite.py` 里，**结构一模一样**。如果记忆分类还用生成式 LLM，就出现了同一类判定逻辑两种实现、两套回退、一份成本——一致性上是亏的。

第三，**成本和延迟**。记忆分类器每轮都调一次，用的还是那个相对贵的模型，而它只需要一个枚举结果。判别式便宜快。

**但有个真实的顾虑，我得说清楚**：`write_user` 和 `write_session` **可以同时为 true**，这是四路组合而不是互斥单选。如果 TypeSafe 那个 SDK 的 Choice 原语支持多选，那没问题；如果只支持单选，就只能拆成两个独立判别点（"要不要写 user 层" + "要不要写 session 层"），调用两次——那反而更贵，得不偿失。**这点我需要先确认 SDK 能力再动手，不能拍脑袋。**

还有个取舍要注意：现在这个分类器**用的是和主对话同一个模型**（deepseek），换成 TypeSafe 就多了一个外部依赖。TypeSafe 未装或未配 Key 时，记忆分类要回退——回退到哪？我的想法是**回退成"都不写"**，因为写记忆是增强动作，判不准就不写，最保守也最安全。这跟检索侧的"回退成不过滤"是不同的哲学，那边宁可多搜，这边宁可少写。

### 事实锚点

| 结论 | 位置 |
|---|---|
| **判定= 生成式 LLM 结构化分类** | `services/chat_long_memory.py:remember_turn`:305-350 |
| 分类结果结构（三字段） | 同上 `class MemoryClassifyResult`:85-96（`write_user` / `write_session` / `reason`） |
| 分类器提示词（四类不写 + 两条原则） | 同上 `CLASSIFIER_PROMPT`:99-124 |
| 温度固定 0 保证可复现 | 同上 `_CLASSIFIER_TEMPERATURE = 0.0`:82 |
| function_calling + 关 thinking | 同上 `_build_classifier()`:183-202 |
| **只把 question 交给抽取**，answer 仅供分类判断 | 同上 `extract_from = [{"role":"user","content":question}]`:315 |
| 抽取侧二次兜底 | 同上 `_EXTRACT_INSTRUCTIONS`:126-131 |
| 写入失败只 WARN 不阻断 | 同上 `except Exception: logger.warning` |

| 两处判定的位置关系 | 分类器在 `remember_turn`（落库阶段）vs 意图路由在 `classify`（请求入口） |

### 边界（如实交代）

- **TypeSafe 的 Choice 是否支持多选，我没验证过**。`write_user` / `write_session` 可同时为 true 是提示词里明写的规则，如果 Choice 只能单选就得拆成两次调用，收益会被成本吃掉。**动手前必须先确认 SDK 能力。**
- 分类器结果**没有落库审计**（模块 docstring「未实现」里列了）。换判别式也一样不解决，这是另一个问题。
- `reason` 字段目前只进日志，不参与决策，也不回传前端。换判别式后这个字段就没了，如果以后要做"为什么这么判"的解释界面，得另想办法。
- 记忆的**过期策略、按 team 隔离、增删改查 API 都没实现**（docstring 明列）。这几个缺口跟判定方式无关，换判别式一个都解决不了。

### 如果被追问，一句话版本

- **为什么不直接用规则判？**→ "用户说我是张三""以后回答简短点"这类能规则化，但"这次先看差旅制度"要判成 session 而非 user，涉及指代和语境，规则写不动。
- **判定不准的后果是什么？**→ 写多了记忆里堆垃圾（还可能污染后续检索），写少了等于记忆功能没用。**不对称的是：写错的记忆很难事后清理**（Mem0 那边只能按 id 删），所以我倾向宁可漏写。
- **抽取为什么不用自己的模型？**→ Mem0 是托管平台，`client.add()` 的抽取在云侧跑，**SDK 不暴露模型参数**，只能靠 `custom_instructions` 约束输出。这是选托管方案的固有代价，要用自有模型就得改 Mem0 OSS 自托管。
- **改的话风险多大？**→ 记忆写入是旁路，判错不影响当轮作答（`remember_turn` 全程 try/except 只 WARN）。风险可控，但要有回退路径。

## Q11. 什么时候会改写 query？第一次用户的问题和建议的检索词是不是一样的？

### 问

什么时候会改写 query？第一次用户的问题和建议的检索词是不是一样的？

### 答（口述）

**改写发生在两个完全不同的时机，我先说第一个：检索之前。**

检索前的改写是**有条件的**，由一个三路判别式做门控：判断这轮问题是「自足」「依赖上文」还是「无需检索」。**只有判成"依赖上文"才调 LLM 改写**。像"今天天气怎么样"这种自足问题，判定完直接跳过改写，检索词就是原问题；像"那谁审批""这个怎么办"这种追问，才值得花一次 LLM 把指代补全成独立可检索的短查询。另外还有个前提——**没有对话历史的时候门控压根不跑**，直接按"自足"处理，因为没有上文可依赖。

**所以第一个问题的答案是：不一定一样，取决于门控判定。** 自足问题两者完全相同，追问问题会被改写。

**再说检索之后的改写**，这是第二处，由 Agent 主动触发：检索回来之后做切题判定，如果判定不切题，Agent 会调 `rewrite_query` 工具换一种问法再检索一次，**本轮最多两次**。这个改写是**模型自己决定要不要调**的，不是我在流程里写死的。

**这里有个设计我觉得值得说：改写词是"建议"不是"命令"。** 我把它拼成一句「建议检索词（可按问题改写后再检索）：xxx」放进 HumanMessage，和「用户问题：xxx」并列，**两者都交给 Agent**。也就是说最终真正送去检索的词，是 Agent 从这两者里自己挑的——它可能直接用建议词，也可能觉得建议词不行、自己重新组织。这个跟传统 RAG 那种"改写完直接替换原问题"的做法不一样，好处是模型有否决权，坏处是多了一层不确定性。

**还有一个区分我特意做了：`question` 和 `query` 是两个独立参数，一路的。** 检索和切题判定都拿得到这两个：切题判定对照的是**用户原问题**，检索用的是**本轮检索词**。为什么不用改写后的词去判定切题？因为一旦改写词本身就偏了，用它判定会把偏的结果当成对的。**评估基准始终是用户原问题，这是我认为这条链路最重要的一个约束。**

另外为了可观测，我给评估结果记了两个字段：首轮词和改写词，前端过程条要展示"首轮词 → 改写词"这个变化过程。

### 事实锚点

| 结论 | 位置 |
|---|---|
| **检索前改写由三路门控决定** | `services/chat_query_rewrite.py:classify`:443-465 |
| 门控三路枚举 | `REWRITE_GATE_CHOICES = ("standalone","needs_context","no_retrieve")` |
| **无上下文时不跑门控**，按自足处理 | 同上 `await self._route_rewrite_gate(question) if context else "standalone"` |
| 只有 needs_context 才调 LLM | 同上 `elif gate != "standalone"` |
| 检索后改写由 Agent 主动调工具 | `services/ai_stream.py:rewrite_query` 工具（约 564-597 行） |
| **本轮最多检索两次** | 同上 `if turn_state["retrieve_count"] >= 2` |
| **建议词与原问题并列给 Agent** | 同上：`f"建议检索词（可按问题改写后再检索）：{plan['query']}"` + `f"用户问题：{question}"` |
| **question / query 双参数分离** | `services/agentic_retrieve.py:retrieve_and_grade`:100-141 |
| **切题判定用原问题、检索用检索词** | 同上 docstring「`question` 是用户原问题（评估切题时对照这个）；`query` 是本轮检索词」 |
| 首轮词/改写词可观测字段 | 同上 `display_query` / `retry_query` / `to_eval` |

### 边界（如实交代）

- **建议词不是强制的**，最终检索词由 Agent 选，可能偏离建议。这是刻意的自由度，但代价是**同一个问题两次运行的检索词可能不同**，评测结果会因此有抖动。
- 门控判错的对称性很好：**判错成"自足"就用原问题去检索，召回差但不报错；判错成"依赖上文"就多调一次 LLM，浪费但无害。** 这个不对称是我敢把门控放在最前面的依据。
- **检索后的改写依赖模型主动调工具**。如果模型不调、或者调了但 `distinct_query` 判定新旧词相同，检索就停在第一轮的结果上——`rewrite_query` 里对"改不出与上次不同的词"是有明确返回的。
- 首轮检索词的生成**依赖 Agent 正确使用工具参数**，如果模型传了个完全无关的 query，`retrieve_and_grade` 里做了兜底：`used_query = query.strip() or question`，空串才回退原问题，非空但离谱的词不会被拦。

### 如果被追问，一句话版本

- **为什么不直接用改写词替换原问题？**→ 那是传统 RAG 的做法。我保留原问题一起给 Agent，让它有否决权，同时**切题判定始终对照原问题**，避免改写词偏了之后自我验证。
- **改写会不会改坏原本好的查询？**→ 会，这是门控存在的理由。所以门控只在"依赖上文"时才放行改写，自足问题一律不改。
- **两次检索的词会重复吗？**→ `distinct_query` 会归一空白后比较，相同返回空串，工具层直接拒绝并说明"无法改写出与上次不同的检索词"。
- **改写词是怎么生成的？**→ 检索前那条由 LLM 按 `REWRITE_PROMPT` 生成（消解指代、抽图谱短实体名）；检索后那条按 `RETRY_REWRITE_PROMPT` 生成，要求"紧扣原问题、不重复上次检索词、可换同义"。

## Q12. 门控判断用的是什么上下文？为什么不加摘要和 Mem0 记忆？

### 问

判断这轮问题是「自足」「依赖上文」还是「无需检索」，用的是历史会话吗？为什么不加上摘要和 Mem0 的记忆？

### 答（口述）

**先纠正一个前提：门控其实连历史都没吃，它只看 `question` 本身。**

调用时我传的是 `state={"question": question}`，就这一个字段。对比一下同文件里的意图路由——那个是 `state={"question": question, "history": context}`，历史是喂进去的。所以准确说法是：**意图路由用热窗口历史，改写门控不用任何上下文**。

**为什么这么设计？我认为是对的，理由是这个判断的性质决定的。**

门控要判的是"这句话**在语法上**是否自足"——有没有"这个""那个""那谁""它"这种**指代或省略**。"那谁审批"这句话本身就有指代，不管我给它多少历史，它依然有指代；"差旅报销标准是多少"这句话本身自足，给多少历史它还是自足。**上下文能帮你把指代补全，但补全不了"这句话里有没有指代"这个判断本身。**

更关键的是：**如果门控吃上下文，就出现了循环依赖**。判断"要不要用上下文"这件事本身需要上下文，判断上下文够不够用又是另一件事。而且多喂上下文会引入一类很糟的错误——**历史里恰好出现过"这个"，模型就把当前这句自足的问题误判成"依赖上文"**，白白触发一次 LLM 改写，把本来干净的查询改坏。

**再说为什么不加摘要。** 摘要是热窗口之外的旧对话的滚动压缩，它解决的是"上下文太长放不下"。而门控是个**廉价判别**——它的输入越少越快越准。加进去等于为了判一句话是不是有指代，先去查十几轮历史、拼一段摘要、再传给判别服务，这个链路收益极低。

**不加 Mem0 的理由不一样，我觉得更值得说。** 长期记忆里装的是用户身份、岗位、偏好这类**跨会话的稳定信息**，而门控判的是**本轮这句话的句法性质**。这两件事在维度上就不一样。举个例子：记住"我是财务部的"确实有用，但用户问"报销标准是多少"这句话依然自足，不需要记忆也知道该怎么检索。**记忆该在的地方是生成答案的时候前置进 SystemMessage，不是在改写门控里。**

**这两条记忆实际注入的位置是答案生成阶段**，我把时序说一下更清楚：意图路由和改写门控跑完之后，才去 Mem0 检索长期记忆、再把摘要和记忆各拼一条 SystemMessage 前置进 messages。所以分工是清楚的——**判定和改写阶段靠热窗口历史轻装上阵，生成阶段才把完整背景交给模型**。

**不过我要主动说一个这个设计的代价**：如果用户的追问指代特别远，指的是热窗口之外的内容，那门控可能判"依赖上文"但改写时拿不到那个指代的对象，改写质量会打折。我现在的做法是改写只吃**最近 12 条（6 轮）**，**消息全文进入、不按条截断**。**这个 12 条是被实测逼出来的**：我原来只回看 4 条，构造了一个"指代对象在第 1 轮、中间隔 8 轮无关话题"的用例，4 条窗口直接把它挤出去了，改写出"报销单需提前几天申请？"（错），12 条窗口才答对"年假需要提前几天申请"。

**单条截断我做过又撤了，这个反复值得说。** 我一度给单条加了上限（用户 200 字、助手 120 字），理由是"助手回答里常含制度原文，喂进去会让检索词被原文带偏"。后来我拿真实数据验证这个理由——从库里取了一条 3012 字的联网检索回答做对照：**全文输入反而多带回了位置靠后的关键词**（问"拒绝日志怎么看"，截 120 字只改出"SELinux 拒绝日志如何查看"，全文改出"SELinux 拒绝日志 ausearch -m avc 怎么看"），检索词并没有被条文带偏。**所以"截断防污染"这个假设是错的，被截掉的那半句往往正好装着指代对象。** 现在只保留一个 30000 字符的硬顶，专门防"用户粘贴整份文档"把上下文撑爆，正常对话不触发。

代价是 prompt 变大：实测典型 6 轮对话上下文 560 字符、709 token；真实数据里助手回答中位数 316 字、p99 2305 字，12 条全量约 2.8 万字符。**换来的是不再有"指代对象恰好被截掉"的盲区，这个取舍我认为值。** 超过 6 轮的指代仍然兜不住——那是把摘要接进改写器才能解的，我没做，见下面的边界说明。

### 事实锚点

| 结论 | 位置 |
|---|---|
| **门控只吃 question，不吃 history** | `services/chat_query_rewrite.py:_route_rewrite_gate` → `system_one(state={"question": question}, ...)`:739-783 |
| **对照：意图路由吃 history** | 同上 `_route_intent`:690 `state={"question": question, "history": context}` |
| 无上下文时门控压根不跑 | `classify`:452-454 `await self._route_rewrite_gate(question) if context else "standalone"` |

### 边界（如实交代）

- **热窗口窗口期的问题是真的**：追问的指代对象若已在最近 12 条（6 轮）之外，改写质量会下降。我靠轮数窗口 + 硬顶缓解，但没根治——**没把摘要接进改写器**。
- **门控判错的后果不对称**：判"自足"→ 用原问题检索，召回差但不报错；判"依赖上文"→ 多调一次 LLM，浪费但无害。所以我把 `None`（判不了）**保守地当作需要改写**。
- 摘要与 Mem0 **只前置进 SystemMessage，不参与判定**。这意味着"用户三个月前说过他是财务部的"这类信息，**不会影响本轮要不要改写检索词**，只会影响生成答案时的措辞。这个边界我认为合理，但它确实是一种取舍，不是最优解。
- 门控判"依赖上文"但 LLM 改写失败时，`query` 回退为原问题（`result.standalone_query.strip() or question`），**此时相当于没改写但仍算走过了改写路径**。

### 如果被追问，一句话版本

- **门控不吃历史会不会判错？**→ 判的是句法性质，上下文改变不了"这句话有没有指代"。而且多喂上下文反而会引入"历史里出现过'这个'就误判自足问题为依赖"这类错误。
- **那摘要不是白做了？**→ 不是。摘要用在生成阶段前置 SystemMessage，让模型知道前面聊过什么；门控不参与摘要。两者服务的是不同阶段。
- **为什么不把三层记忆都喂给 Agent？**→ 已经在做（摘要 + 长期记忆各一条 SystemMessage 前置）。但**刻意不前置热窗口的完整历史**，那部分已经通过改写后的检索词转达了，再喂一遍等于重复且稀释注意力。
- **如果用户指代跨越很远怎么办？**→ 当前会退化——这是已知缺口。彻底解法是把摘要也接进改写器，但那样会增加门控输入、降低判别准确性和速度，是个权衡。

## Q13. 意图路由为什么只用热窗口历史？加上摘要和 Mem0 是不是更好？

### 问

意图路由为什么只用热窗口历史？加上摘要和 Mem0 的记忆是不是更好？

### 答（口述）

**先说结论：我认为不加是对的，而且意图路由"吃历史"的必要性比门控还低。** 这不是省事，是它的输出性质决定的。

**意图路由和门控的差别在于"错判的后果"。** 门控错判只影响一句 query 的措辞；**意图路由的输出直接决定给 Agent 挂哪些工具**——判成 kb 就挂知识库检索，判成 web 就挂联网搜索，判成 chitchat 就什么都不挂、只闲聊作答。所以它的判错是**功能级的**：把制度问题判成闲聊，用户就啥也搜不到。

正因为错判更严重，我更不敢往里塞噪声。加了摘要和 Mem0 之后输入变长，而意图分类是五选一，**上下文一多最容易出的错就是"看到关键词就归错类"**。举个例子：用户长期记忆里有"我是做财务的"，某天他问"最新的差旅政策有变化吗"——记忆里"财务"这个词可能把判别式往 `profile`（个人偏好）那边拽，可这其实是个 `kb_then_web` 的问题。**记忆在这里是噪声，不是信号。**

**再说热窗口为什么够用。** 意图路由判的是"**这轮要不要用检索工具**"，而这个判断的信息量需求本来就不高——大部分问题单看这句话就能判。真正需要历史的只有一种情况：短促的追问，比如上一轮问差旅、这轮问"那住宿标准呢"，不看历史不知道这是知识库问题。**最近 12 条（6 轮）足够覆盖这种衔接。** 这个数是我调过的：一开始只回看 4 条，后来构造了"指代对象在第 1 轮、中间隔 8 轮无关话题"的用例，4 条直接把它挤掉、改写结果错了；放到 12 条才稳定覆盖。再往前的历史对"这轮要不要检索"确实没有增量，所以没继续放大。

**另外我想强调一个不对称：意图路由和改写器共用同一份上下文，而门控完全不吃上下文。** 这份上下文是**消息全文进入、不按条截断**的。这一点我改过一次：原来做过助手侧截 120 字、用户侧 200 字，理由是"助手回答里的制度原文会干扰判别"。但实测这个理由站不住——拿真实的 3012 字长回答做对照，全文输入没有把判别带偏。**所以这里的取舍改成了"信息完整优先，只留硬顶防爆"。同一份上下文，两个判定的用法仍然不一样：路由把它当"这轮在聊什么"的背景，门控根本不看它。**

**那 Mem0 到底该不该进意图路由？我认为不该，理由很硬**：长期记忆描述的是"**这个人是谁**"，而意图路由判的是"**这句话要干什么**"。这两件事在维度上就不一样。用户是财务部的人，这是身份；他说"报销标准是多少"，这是知识库查询——身份跟意图没有必然联系。**记忆该在的地方是生成答案时前置进 SystemMessage 帮模型理解背景，不是在路由阶段影响工具选择。**

**最后我要主动说一个更激进的取舍：意图路由其实可以完全不吃历史。** 如果我接受"短追问判错就判错"，让它退化成纯单条判断，链路能再简一层、判别也能更稳。我现在保留历史是留了余量——**但我不打算再加摘要和 Mem0**，因为那是往一个只需要局部信息的判定里灌全局信息，收益为负。

### 事实锚点

| 结论 | 位置 |
|---|---|
| **意图路由的输入只有 question + 热窗口** | `services/chat_query_rewrite.py:_route_intent`:702-704（`state={"question":...}` + `if context: state["history"]=context`） |
| **上下文全文输入**：窗口 12 条、单条不截断、硬顶 30000 字符 | `services/chat_memory.py:30-33`（`_REWRITE_HISTORY_WINDOW=12`、`_REWRITE_CONTEXT_MAX_CHARS=30000`） |

### 边界（如实交代）

- **跨轮话题跳跃会失效**。如果用户在第 10 轮突然问一句"那报销期限呢"、而中间 9 轮全在聊别的，最近 12 条（6 轮）兜不住，这轮可能被判成自足问题、不触发改写。这是**已知缺口**：窗口从 4 条放宽到 12 条、并把单条截断改成全文输入，缓解了"指代在 4 轮外"和"指代被截掉"两种情况，但超过 6 轮仍然丢。
- **意图路由的准确率我没有单独测过**。评测集测的是检索质量（hit@1 / recall@5），**路由判对判错不在指标里**。所以"意图路由判得准"这句话我只能从逻辑上说，**没有数据支撑**——这是当前评测体系的盲区。
- 意图与门控**共用一份压缩上下文**是简化，不是最优。如果两者对上下文的诉求继续分化（比如意图路由想更宽、门控想更窄），应该拆开。
- `graph_queries` **仅 kb 轮次保留**，其余意图一律清空——意图判错会连带把图谱检索词也丢掉。

### 如果被追问，一句话版本

- **多给上下文不是"更聪明"而是"更容易偏"。** 五选一的分类任务，上下文里的每个词都可能成为干扰线索，尤其当记忆里带身份、岗位这类高辨识度的词时。
- **为什么意图路由要历史、门控不要？**→ 意图路由判"要不要检索"，短追问需要看上一轮才知道在问什么；门控判"这句话有没有指代"，这个性质由句子本身决定，历史改变不了。
- **如果用户明确说"记住我偏好简短回答"呢？**→ 那是长期记忆的用途，在生成阶段影响措辞，不该让它去改"挂不挂检索工具"这种功能决策。
- **路由判错的代价怎么量化？**→ 目前**没量化**。这是我认为评测体系最该补的一块——应该单独构造一组"路由混淆"用例，比如"个人偏好类问法里其实问的是制度"，看误挂/漏挂工具的比例。

## Q14. 知识图谱是怎么设计和使用的？

### 问

你的项目里知识图谱是如何设计的和使用的？

### 答（口述）

**先给模型：图谱只有四层，节点三类边两种。**

文档节点连到分块节点（HAS_CHUNK），分块节点指向它提到的实体（MENTIONS），实体之间是 RELATED_TO。所以查"这篇文档讲了什么"就是从文档往下走两跳。**刻意做成这么浅**——图的价值在关联，不在深度遍历。

**关于边类型我要说明一个刻意的简化**：Neo4j 里的边类型**只有 RELATED_TO 一种**，真正的语义关系（比如"财务部负责差旅报销"的 RESPONSIBLE_FOR）**存在边的属性 `relation` 里面**。为什么这么做——因为语义关系有 12 种，如果每种都建成独立的边类型，抽取的时候模型返回的类型经常对不上（它可能自造一个 APPLIES_TO），就会产生一堆碎片化的边类型没法查询。**用一个统一的边类型 + 属性存语义，好处是查询时不用关心边的具体类型，抽取时容错也高**，代价是失去了 Neo4j 按边类型高效检索的能力。同理实体类型有 10 种，但**未知类型一律兜底成 CONCEPT**，不丢数据。

**抽取是 LLM 做的，但输出结构我刻意放松了。** 实体和关系的类型字段我用的是 `string` 而不是 pydantic 的 `enum`，然后在代码里 `normalize` 到枚举。原因是实测模型很爱返回中文类型或者自己造一个类型，**如果用 enum 严格校验，整块抽取会直接失败全丢**——现在这样顶多是归到 CONCEPT，数据保住了。另外关系字段名必须是 `relation`，但我**额外留了一个 `type` 字段做兼容**，因为模型经常把关系类型写成 type。

**构建流程是 clear before build**：每次重建一篇文档的图，先删旧数据再重建。这样能天然避免残留脏边，代价是每次全量重抽。启动时我会幂等建三个唯一性约束，这里有个教训——**没有唯一性约束的话 MERGE 不是原子操作**，我曾经观测到同一个 documentId 建出了 4 份重复的文档节点；加上约束之后并发 MERGE 会拿到 transient error，我这边自动重试就解决了。

**使用上，图谱是 Agent 的一个独立工具，不参与 RRF 融合。** 这是一个我主动做的取舍：关键词和向量两路召回是**互补**的，用 RRF 融合合理；但图谱是**另一种知识形态**——它回答的是"谁负责什么""这些是什么关系"，不是"这段文字讲了什么"。硬塞进 RRF 融合里，语义对不上，分数也没法比。所以我把它做成 `retrieve_graph` 工具，**Agent 自己决定要不要调**，调了就把结果作为一个独立段落拼进上下文。

**工具入参有个讲究：必须传短实体名，不能传整句。** 所以在改写那个阶段我会让 LLM 顺便抽出图谱短实体名，比如"发票如何报销"要拆成"发票、报销"，禁止出现"流程""要求""如何"这类词。

**匹配策略上我踩过一个坑并修正了**：一开始用 CONTAINS 模糊匹配，结果搜"发票"命中了整篇《发票管理办法》的标题，噪声极大。**改成相等、前缀、后缀加别名匹配，不用 CONTAINS**。另外实体名我做了书名号归一——去掉《》再比，这样能同时匹配到带书名号的旧节点和新建的不带的节点。

**最后一点我觉得最重要：图谱上下文明确声明"不能当制度原文"。** 拼进模型上下文时我加了免责句，跟长期记忆那句"以本轮检索资料为准"是同一个思路——**图谱给的是关系线索，不是条款原文，回答制度问题必须回到向量和关键词召回了原文。**

- **图谱评测只有 19 条**，是三个评测集里最小的（检索 148、生成 58）。负例只有 3 条，**这个样本量不足以支撑"图谱有效"这种结论**，只能说"能跑通、基本准确"。
- **实体类型和关系类型是拍脑袋定的 10 种和 12 种**，没有做过领域适配。落到具体企业知识库很可能不够用，缺类型时只能兜底成 CONCEPT——**兜底多了图谱的区分度就下降了**。
- **抽取质量完全依赖 LLM**，我没有做抽取质量的自动评测（比如人工标注一批三元组算准确率）。目前只有"能抽出来"和"能查出来"两层验证。
- **语义关系藏在属性里，代价是无法按关系类型高效查询**。想查"所有 RESPONSIBLE_FOR 的边"只能全扫再过滤。
- **`related_to` 之外的关系其实是弱监督的**——关系类型由 LLM 判断，weight 是它自报的可信度，**没有经过校准**，不能当置信度用。
- **图谱不参与 RRF 融合**是取舍不是定论。更完整的做法是把图谱当作第三路召回也进融合，但需要解决"关系类结果与文本类结果分数不可比"的问题，我没有验证过这条路。

### 如果被追问，一句话版本

- **为什么要图谱，向量检索不够吗？**→ 向量检索回答"这段文字讲了什么"，图谱回答"谁负责什么、这些是什么关系"。多跳问题是向量的弱项——问"A 部门的人出差，B 部门呢"这类需要关系跳跃的，向量只能靠碰巧把两段都召回。
- **抽取不准怎么办？**→ 靠三层兜底：类型字段用 string 不做 enum 校验、`normalize` 归到 CONCEPT、关系字段名兼容 `type`。**宁可类型粗一点，也不要丢整块抽取。**
- **图谱和多跳检索什么关系？**→ 图谱本质是为多跳设计的，但我的多跳评测（16 条）测的是混合检索能不能召回两段，**不是靠图谱答的**——图谱是给 Agent 的独立工具，不在 RRF 里。
- **重建成本？**→ clear before build 是全量重抽，成本高。我有 `reindex_all_kg.py` 全量脚本，但**没做增量更新**，这是明显的缺口。

## Q15. JWT 是什么？你的项目里怎么设计的？

### 问

JWT 是什么？你的项目里如何设计的？

### 答（口述）

**JWT 是一个自包含的令牌格式**——三段用点连接的 Base64 字符串：header、payload、signature。服务端把身份信息签进 payload 并用密钥签名，之后客户端每次请求带上它，服务端**只验签、不查库**就能确认身份。核心价值是**无状态**：不需要服务端存 session，多副本部署天然友好。

**我的设计是双令牌：access 两小时、refresh 七天。** 两个令牌的 payload 结构完全一致，只有 `type` 字段区分。登录时一次签发两个，access 用来调接口，过期了拿 refresh 换一对新的。签名用 HS256 对称加密——签发和验证同一个密钥，单服务架构没必要上非对称。

**payload 里我只放四个字段**：`sub`（用户 ID）、`username`、`type`、`exp`。这里有个刻意的选择：**payload 里不放权限**。因为权限变更要立刻生效，而 JWT 是签发那一刻就固化的，放进去得等 token 过期才生效。所以我每个请求都查一次库拿最新权限——代价就是每次请求一次权限查询，这个开销在压测里我还专门处理过。

**校验分两层，顺序有讲究。** 先验签和过期时间，再**校验 type 等于 access**。第二步是最容易漏的一环：因为两个令牌算法一样、结构一样，唯一的区分就是这个 type 字段。**少这一步，refresh token 就等价于一个七天有效的 access token**——任何拿到它的人都能直接调接口。

**然后是几个安全细节。**

错误文案统一：过期、签名不符、格式非法都返回同一句"未登录或 token 已失效"，**不泄露具体原因**，避免给攻击者反馈信号。登录也做防枚举：用户不存在和密码错误返回同一句"用户名或密码错误"，不告诉对方这个用户名已注册；但账户禁用会明确提示。

密码这块有个坑我处理了：bcrypt 5.0 对**超过 72 字节**的密码直接抛 ValueError，而 4.x 是静默截断。所以我在 DTO 层加 `max_length` 粗筛，服务层再按 UTF-8 字节数校验一次。**24 个汉字就到顶了**，如果只靠字符数校验，用户以为设了 20 位密码、实际只有前 24 字节生效，这是很隐蔽的问题。

密码重置的验证码是 6 位随机数、存 Redis 十分钟、六十秒发送冷却，而且**邮件发送失败会补偿回滚删码**——否则用户看到失败提示但码还留在 Redis 里，是个可被利用的窗口。

### 事实锚点

| 结论 | 位置 |
|---|---|
| 双令牌 + 默认时长 | `services/auth.py` docstring:3-4（access 2h / refresh 7d）；`core/config.py:39-40` |
| **payload 四字段**（sub/username/type/exp） | `services/auth.py:_sign_token` |
| HS256 对称签名 | 同上 `jwt.encode(..., algorithm="HS256")` |
| **refresh 时校验 type** | 同上 `if payload.get("type") != _TOKEN_TYPE_REFRESH` |
| **access 侧也校验 type（防 refresh 当 access 用）** | `api/auth_route.py:authenticate_request`「校验 type=access」 |
| 错误文案统一不泄露原因 | `auth_route.py`：过期/签名不符/格式非法统一文案 |
| 登录防枚举 | `services/user.py:validate_credentials`（不存在与密码错误同句） |
| **bcrypt 72 字节 + DTO 与服务层双重校验** | `schemas/auth.py:44`（`BCRYPT_MAX_PASSWORD_BYTES=72`）+ docstring:14-25 说明 |
| 密码重置：Redis 10min / 60s 冷却 / 失败补偿删码 | `services/auth.py:send_reset_code` |

### 边界（如实交代）

- ⚠️ **refresh token 无状态、无吊销机制。这是代码注释里我自己写下的**：「旧 refresh token 在过期前始终可用。接入黑名单 / 轮换是后续增强项。」
  后果是：**用户改密码或被禁用后，之前签发的 refresh token 在 7 天内仍能换出新 access token**；登出也只是前端删令牌，服务端不知道。这是纯无状态方案的固有代价，要解决就得引入服务端存储（黑名单或轮换），那等于部分放弃 JWT 的优势。**这是我知道、还没做的一件事。**
- ⚠️ **令牌存 localStorage，没有 HttpOnly Cookie**。这意味着如果出现 XSS，令牌能被脚本读走。改成 HttpOnly Cookie 更安全，但那会引入 CSRF 防护需求（SameSite + CSRF token），是一整套改动，**我没做**。
- **access 有效期 2 小时偏长**。业界理想是 15-30 分钟加刷新，我选 2 小时是为了减少刷新调用次数——刷新要查库建会话，在并发压测里这部分开销不小。**这是明确的取舍不是最优解。**
- **每次请求查一次权限、无缓存**。安全上是对的（权限变更立即生效），但性能上是持续开销。
- 单密钥 HS256，**没有密钥轮换机制**；也没有 kid（key id）header 支持多密钥并存。

### 如果被追问，一句话版本

- **为什么不把权限放进 JWT？**→ 权限变更要立刻生效，JWT 签发即固化，放进去得等过期。所以每次请求查库换实时性。
- **JWT 会被盗用吗？**→ 会，所以 access 压到 2 小时；真正的防护应该靠 HttpOnly Cookie 挡住 XSS 读取，我这块没做。
- **怎么主动失效？**→ 现在做不到。要做就得加黑名单或 token 版本号、服务端存一点状态，也就放弃了纯无状态。
- **为什么不用 session？**→ session 要服务端存储且有并发共享问题；JWT 把鉴权变成纯验签，适合多副本部署。
- **刷新令牌时要不要重新查用户状态？**→ 要，而且这里正好是个好处：refresh 时重新 `build_auth_user`，**所以账号被禁用或软删后，刷新会失败**——只有 access 有效期内的旧令牌还能用。

## Q16. token / 成本核算怎么做的？为什么不用 Langfuse？

### 问

讲一下你的 token 和成本核算怎么做的，为什么不用 Langfuse？

### 答（口述）

**先纠正一个前提：我用了 Langfuse，而且是自托管的。** 但它和我的本地核算**不是替代关系，是互补**。所以这个问题我得分两层答。

**先说本地这套。** 我在进程内维护一个 `TurnUsage`，一轮问答里的每一次 LLM 调用都往里累加调用次数和 token 数。实现上有个关键选择：**用 ContextVar 传递，不用显式传参**——因为调用链很深，agent 主循环 → 工具 → 改写/切题判定，靠参数传会污染一长串函数签名。

**token 数取真实值，不猜。** 我从 LangChain 的回调结果里取，兼容两种形态：新版在 `generations[].message.usage_metadata`，旧版在 `llm_output.token_usage`。**取不到就返回空，不按字数估算**——估出来的数字会污染成本口径。

**金额是估算的，而且我在字段名上就写明了。** 单价配在配置里（输入 2 元、输出 8 元每百万 token），算出来的字段叫 `estimatedCostYuan`，**只用于"发现异常用量"，不作账单口径**。这个区分我很在意——如果字段名叫 cost，早晚有人拿它对账。

**挂载点我选在 LLM 构造器上，不是 invoke 调用点。** 因为构造点只有 8 个（agent、改写、切题、记忆、摘要、KG 抽取、OCR、评测判分），而 invoke 调用点更多且会持续新增。**挂构造器是"加一次全覆盖"，不会随新代码漏统计。**

**限流是另一件事，按"轮"限不按 token 限。** Redis 计数，窗口 25 小时（24 小时窗口加 1 小时缓冲，避免时钟漂移导致提前过期）。**为什么按轮不按 token**：用户能理解、实现简单，也不会因为一次长上下文就把正常用户误杀。**Redis 不可用时 fail-open**——限流是保护措施，不该因为它自己挂了就挡住所有人，这跟 ES、Neo4j 的降级风格一致。另外计数在放行前自增，宁可多算一次也不放过多调一次。

**然后说 Langfuse 这边。** 我确实接了，而且是**自托管**。用 Langfuse 的原因很实际：**数据不出本机、不依赖 SaaS 配额**——这个项目已经因为外部额度耗尽被中断过两次。

**但它刻意不进关键路径。** Langfuse handler 是懒加载的：SDK 没装或没配 Key 就完全不加载，零开销、CI 不受影响；初始化失败只记 WARN；上报是异步旁路，**Langfuse 挂了只是丢观测数据，不影响任何一次对话**。这里有个本质区别我想说清楚：**限流必须在关键路径、必须同步、强一致；观测可以在旁路、可以丢。** 这两者的可用性要求完全不同。

**两个我实测过、值得说的结论：**

第一，**成本口径两边是对齐的**。我验证过本地估算出的金额和 Langfuse `cost_details.total` **逐位一致**——0.000398 元对 0.000398 元。两条完全独立的计算路径吻合，这个交叉验证让我对本地那套比较有信心。

第二，踩过一个坑：**Langfuse 只认它内置价格表里的模型名**。我用的模型别名它不认，于是它照常记 token 用量，但 `cost_details` 是空的、成本看板恒为 0。得手动注册单价脚本。**这里还有个细节**：Langfuse 的 `inputPrice` 是**单 token 价**不是"每百万"，内置 babbage-002 是 4e-07（即 0.4 美元/百万），配错量级就会差一百万倍。

**所以总结我的取舍：两套都要，因为它们能回答不同的问题。** Langfuse 回答"这次请求内部发生了什么"——能下钻到工具调用、prompt 全文、每步耗时；本地那套回答"这个用户今天用了多少钱"——**不连任何外部服务就能断言，而且能同步拦住超限请求**。Langfuse 挂了本地照常工作；反过来说，也只有本地那套能在 CI 里断言成本。

- ⚠️ **自托管 Langfuse 的代价是实测出来的，不是估算**：整个栈约 2.6 GB（ClickHouse 1.2 + web/worker 1.2 + MinIO 0.1 + PG/Redis 0.06）。本机 Docker VM 只有 7.7 GB 且已跑 16 个容器，加上它之后 **PostgreSQL 后端进程被 OOM 杀掉、进入 crash recovery**。所以只能按需启停。**这个代价是我实测踩出来的，不是看文档知道的。**
- **单价是配置里手填的，不是从供应商拉的**。模型涨价或换模型，忘记改配置，成本估算就偏了。**没有自动同步机制。**
- **限流只限"轮次"，不限 token**。所以一个构造超长上下文、疯狂调工具的用户，单轮能烧掉远超正常用户的额度。这是刻意的（防误杀），但**是真缺口**。
- **限流的计数在 Redis 里，没有和实际账单对账机制**。如果中间有 Redis 重启或 key 过期，计数会丢。
- **Langfuse 只做 trace 下钻，没有接它的评测/数据集/评分功能**。那部分我是自己写的脚本（`eval_retrieval.py` / `eval_generation.py` / `eval_graph.py`），没有复用 Langfuse 的评测能力——**这部分是重复建设，我知道**。
- **金额估算没做多模型区分**：所有 LLM 用同一个单价对。但我的模型（deepseek）和 reranker（qwen）单价不同，**严格说估算会偏**。这是我目前口径粗糙的地方。

### 如果被追问，一句话版本

- **为什么不只用 Langfuse？**→ 它是异步旁路、挂了不影响对话，但限流必须同步拦截；而且成本断言要能不连外部服务跑（CI 里用）。
- **为什么不自己造 trace 系统？**→ 没意义。trace 下钻要的是"prompt 全文 + 每步耗时 + 工具调用"，自己造就是重复实现 Langfuse 已经做好的部分。我只在它缺的地方补——**限流和同步成本断言**。
- **估算和实际账单差多少？**→ **我没法回答，因为我拿不到实际账单。** 我只能保证本地估算和 Langfuse 的 `cost_details` 一致，那是两条独立路径的交叉验证，不等于和供应商账单一致。
- **成本数据落在哪？**→ 每轮一条结构化日志，字段是 `llmCalls / promptTokens / completionTokens / totalTokens / estimatedCostYuan`。**没有入库，没有 dashboard 历史查询**——要查趋势得翻日志或用 Langfuse。这是缺口。

## Q17. 你是怎么设计自测的？为什么这么设计？

### 问

讲一下你是如何设计自测的，为什么这么设计？

### 答（口述）

我把自测分成三层，从快到慢、从轻到重，**每一层解决不同的问题**。

**第一层是单元测试，16 个文件，跑得极快、不依赖任何外部服务。**

设计的关键是**把业务逻辑从外部依赖里剥出来**。举个具体例子：RRF 融合那个测试，我不启动真实的 PG、不调真实的 ES，而是手写一个"假会话"对象，它被调用时直接返回我预置的行数据。这样测试的就是**纯粹的融合逻辑**——两路都命中的 chunk 是不是排在前面、每路的原始分有没有透传、空 query 是不是返回空列表。权限那个测试也是同样手法，用一个按调用顺序返回预设结果的假会话，验证直接权限和角色权限有没有合并去重、拿到 ADMIN 角色会不会自动追加管理员权限码。

**为什么要这么设计？因为大部分 bug 都不是"PG 挂了"这种环境问题，而是"逻辑算错了"。** 用假对象测逻辑，跑得快、失败信息准，而且**CI 里不需要起数据库**，几秒钟就能跑完。代价是测不到真实的 SQL 和 ES 查询对不对——所以这只是第一层。

**第二层是冒烟脚本，62 个，专门测真实链路。**

单元测试说"逻辑对"，但不说"接起来还对"。比如权限可见性，真实环境里 ES 那边字段类型如果被动态映射建成 text，过滤会**静默失效**——不报错，只是不生效。这种问题只有真连库才测得出来。所以我有一批 `smoke_*.py` 脚本，起真实的 ES、PG、Neo4j，跑真实的增删改查和检索，把整条链路走一遍。**这一层慢、但抓的是单元测试抓不到的问题。**

**第三层是我认为最值钱的一层：评测集 + 评测脚本。**

我建了三份评测集——检索 148 条、生成 58 条、图谱 19 条。每条都是人工标注的"标准答案"，然后写脚本让系统跑一遍、自动算指标：hit@1、recall@5、多跳全命中率、要点覆盖率、忠实度这些。

**但这里有个坑，是我踩过两次才想明白的：评测集本身也会错。** 最容易出的错不是逻辑错，而是**打错文档标题**、期望要点跟文档对不上。后果特别隐蔽——那题永远"未命中"，你会以为检索不行，其实是标注错了；或者分数虚低，你据此去调参，越调越偏。

所以我写了一个**校验评测集的脚本**，先检查每个期望的标题在库里到底存不存在、期望要点能不能在对应分块里找到。这就像**考试前先对答案**。

**然后是我最想讲的一个设计：把文档里的数字绑进 CI。**

我发现项目栽过两次，**都是文档里的数字过期了**：一组连接数在三个文档里写成 16、31、32、40；README 说"难题 21 条"，实际评测集里是 51 条。这类错误的共同点是——**文档写错不影响任何测试，永远不会被发现，直到面试被追问才暴露**。

所以我写了 `check_doc_numbers.py`，思路很简单：**每个数字只有一个权威来源**（比如"评测集总条数"就从 jsonl 里数，不从文档抄），文档里声称了哪个数字就登记进去，对不上就**让 CI 失败**。

这里有个细节我觉得挺妙：**如果脚本里的模式没匹配到任何内容，它也失败**。因为文档被改写、格式变了，校验会静默失效——**那比没有校验更糟**。我还给它加了个自检开关，改校验规则后必须先跑自检。

**最后是 CI 跑什么**：静态检查、类型检查（要求零问题）、单元测试、文档数字校验，前端还有类型检查和生产构建。**门槛全部挂在 CI 上而不是靠自觉**，因为"靠自觉"这件事在我身上已经被验证过是不成立的。

### 事实锚点

| 结论 | 位置 |
|---|---|
| **三层自测结构** | 单元测试 16 个（`backend/tests/`）+ 冒烟脚本 62 个（`backend/scripts/`）+ 三份评测集 |
| **单元测试用假会话 mock 外部依赖** | `tests/test_search_rrf.py`（`_FakeSession.execute` 直接返回预置行）+ docstring「mock 掉两路召回与 PG 查询」 |
| 权限测试按调用顺序返回预设结果 | `tests/test_permission_matrix.py`（`_QueuedSession`：direct → via_role → role_code） |
| 静态检查 + 零问题类型检查 + 单测 | `.github/workflows/ci.yml`：ruff → mypy → pytest -q |
| **文档数字校验挂进 CI** | 同上 step「文档数字校验（文档里写的数字 vs 源码 / 评测集）」 |
| **数字校验的设计：单一权威来源 + 声称登记** | `scripts/check_doc_numbers.py` docstring:11-19（`FACTS` / `CLAIMS`） |
| **栽过的两次：文档数字分叉** | 同上:5-9（同组连接数 16/31/32/40；README「难题 21 条」实为51 条） |
| **模式未命中也失败（防静默失效）** | 同上:17-19 |
| 校验规则改动需跑自检 | 同上 `--self-test` 参数 +:26-28 |
| **评测集校验（防"标注错→指标骗人"）** | `scripts/validate_eval_set.py` docstring:3-14 |
| 「难题」口径全项目唯一定义 | `check_doc_numbers.py:58-59`（`difficulty == "hard"` 且非多跳；注释要求 README/简历/面试稿统一用它） |
| 源码规模数字从磁盘现算 | 同上 `_code_facts`:74-100 |
| 实测数字（无法推导）人工维护但强制一致 | 同上 `MEASURED_FACTS`:101-106 |

### 边界（如实交代）

- ⚠️ **单元测试测不到真实 SQL 和 ES 查询**。这是 mock 换来的代价。权限字段被建成 text 导致过滤静默失效那类问题，**只有冒烟脚本能抓**——所以两层必须都在，缺一层就是盲区。
- **评测集是我自己标的**，不是第三方标注。虽然有校验脚本保证"标题存在、要点能找到"，但**"该标注为命中"这个判断本身是我的标准**，无法交叉验证。这是自标的固有局限。
- **评测集只有 148 条**，广度有限——它测的是"我关心的那批问题"，不代表真实用户问题的分布。
- **`check_doc_numbers.py` 只能校验"能从源码/评测集推导"的数字**。压测峰值连接数这种**实测数字无法推导，只能人工维护**（`MEASURED_FACTS`），脚本只能保证它在各文档之间一致，不能保证它没过期。
- **冒烟脚本不在 CI 里跑**，因为要起真实依赖、慢。所以它们是"我本地定期跑"，不是"每次提交都跑"，**这是覆盖率的缺口**。
- **没有测试覆盖率指标**。我知道哪些逻辑有测试，但不知道"百分之多少的代码被覆盖了"，也**没做过覆盖率分析来找盲区**。

### 如果被追问，一句话版本

- **为什么 mock 而不是真连库？**→ 单元测试要测的是"逻辑算没算错"不是"环境能不能用"。真连库慢且脆，CI 里也跑不动。代价是测不到真实查询——所以我加了冒烟脚本层。
- **评测脚本和自己写的单元测试有啥区别？**→ 单元测试的"标准答案"是我在代码里写死的期望；评测集是**独立的标注数据**，它能发现"功能和需求理解不一致"，这是写死期望值测不出来的。
- **校验评测集的意义？**→ **防"标注错 → 指标骗人 → 据此调参 → 越调越偏"这条连锁。** 最隐蔽的失败不是代码有 bug，而是你的尺子本身坏了。
- **为什么把文档数字校验也做成 CI？**→ 因为文档数字错误**不影响任何测试**，是所有错误类型里唯一"完全不会自己暴露"的。与其指望有人核对，不如让机器核对。
- **这套自测最大的盲区？**→ **冒烟脚本不在 CI 里**，以及**没有覆盖率分析**。前者靠自觉，后者没做。

## Q18. 详细讲三份评测集怎么设计的，是否用了 LLM？

### 问

详细讲一下检索 148 条、生成 58 条、图谱 19 条，每个测试是如何设计的？是否使用 LLM？

### 答（口述）

**先直接回答"是否用 LLM"——三份的答案不一样，这是我刻意的划分。**

| 评测集 | 判分方式 | 用不用 LLM |
|---|---|---|
| 检索 148 条 | 确定性：标题字符串匹配 | **判分不用**，但链路里有 reranker |
| 生成 58 条 | 两档：确定性指标 + LLM 判分 | **部分用**（忠实度、引用准确率） |
| 图谱 19 条 | 确定性：实体名与关系对匹配 | **不用** |

**原则是：能用确定性规则判的，绝不交给 LLM 判。** LLM 只用在"判断一段话是否被资料支撑"这种规则写不出来的指标上。

---

**先说检索 148 条——这是设计最用心的。**

每条只有四个字段：问题、期望文档标题列表、期望关键词、类别。**判分方式是字符串匹配**：把系统返回的 top-k 文档标题跟期望列表求交集，命中就算，位置就是名次。所以这一份**完全不花 LLM 调用，可进 CI**。

但真正难的是**指标怎么算**，这里我踩过坑。**单跳和多跳必须分开统计**，因为语义根本不同：

- **单跳是"任一命中"**（any-of）——期望的几篇文档里召回任意一篇就算对
- **多跳是"缺一不可"**（all-of）——所有期望文档都必须进 top-k

**为什么必须分开？** 因为如果混在一起算，单跳的 recall 会**把多跳的部分命中状态掩盖掉**。比如一道两跳题只召回了其中一篇，在 all-of 语义下算失败，但混进单跳的平均值里，就变成了"部分得分"，把失败信号冲淡了。

所以多跳我单独给三个指标：**全命中率**、**部分命中率**、**文档召回率**（平均检索到多少比例的期望文档，比如两跳题会得到 0、0.5、1.0 这三种值再平均）。**"部分命中率"这个指标是为了区分"完全找不到"和"找到了但没找齐"**——这两种失败原因需要的改进方向完全不同。

还有一个设计：**单跳和三跳还按难度分组统计**。因为简单题如果都满分，混合平均会被淹没，看不出难题上有没有进步。所以我按 `difficulty` 字段分开打印。

**这一份有个必须讲的技术处理：冻结查询向量。** embedding 服务端存在浮点非确定性——**同一段文本两次调用，返回的向量是不一样的**。不冻结的话，同一份评测集每次跑总会在一两道题上飘，**你根本分不清是参数改了导致指标变化，还是随机噪声**。所以我把每道题的查询向量算一次就落盘缓存，之后所有跑都用同一份向量，跨运行严格可比。

另外脚本里有个降级检测器，统计 rerank 和 embedding 各自失败多少次。**因为降级会静默改变指标**——rerank 挂了会降级成 RRF、minScore 过滤失效、负例全进来；向量化挂了会退化成纯 BM25。**如果不显式提示，我可能把这个当成"参数调坏了"，往错的方向调。**

---

**再说生成 58 条——这一份必须用 LLM，但只用在两个指标上。**

字段是：问题、是否可回答、期望要点、期望文档、类别、难度。构成上 **51 条可回答 + 7 条不可回答**，难度 **28 简单 + 30 困难**。

指标我分成**两档**：

**确定性档（不花 LLM）**——要点覆盖率（答案里出现了多少期望要点）、引用率（多少回答带了 `[n]`）、**引用越界**（`[n]` 的编号超出了实际资料条数，这是硬错误）、拒答率（不可回答的问题里有多少正确地说了"没有相关内容"）。

**LLM 档（可关，--no-judge）**——**忠实度**（把回答拆成若干条断言，逐条判断能否被资料支撑，算支撑比例）和**引用准确率**（`[n]` 是否指向真正支持该句的资料）。

**为什么只有这两个要 LLM？** 因为它们要判断的是"一段话是否被另一段话支撑"，这种语义关系写不成规则。而要点覆盖率、引用越界这种都能数出来，用 LLM 判反而是引入噪声还花钱。

**判分器里有个细节我很在意：我特意写了很长的编号口径说明防止 LLM 误判。** 因为一个编号对应的是**一整条资料的原文**（可能很长、包含多个小节甚至一张表格），只要断言在这段原文里**任意位置**能找到依据就算对。**如果不写清楚，LLM 很容易因为"这句话属于哪一小节"而判错引用。** 提示词里明确写了"切勿因为这句话在原文里属于哪一小节而判错"。

判分失败（没配 Key、网络、结构化解析失败）我返回空值、**fail-open 不算成回答错误**——跟切题判定是同一个约定。

---

**最后说图谱 19 条——这份单独做的理由很直接。**

检索那 148 条测的是"混合检索"，**图谱通道完全不在里面**。所以"图谱检索可用"这句话在简历和口述里是**没有证据的**。这一份专门补这个证据——**只测图谱通道本身，不涉及生成**，所以完全不用 LLM。

19 条分三类：**实体召回 12 条**（期望实体能不能被检索出来）、**关系召回 4 条**（期望的 source→target 关系对能不能返回）、**负例 3 条**（图谱里不存在的概念应返回空，而不是硬凑）。

它有个别的评测集都没有的指标：**出处覆盖率**——返回的关系里带 `evidence` 的比例。这条直接验证"每条关系都能回溯到来源片段"这个宣称。

### 事实锚点

| 结论 | 位置 |
|---|---|
| **三份评测集的判分方式差异** | 检索/图谱 = 确定性匹配；生成 = 确定性档 + LLM 档（`eval_generation.py` docstring:8-21） |
| **检索集字段**（question/expect_documents/expect_keywords/category） | `backend/eval/rag_eval.jsonl`（实测 148 条；category: oss 39 / travel 20 / release 15 / confusable 15 / shenlun 13 / negative 12 / multi_hop 16 / resume 10 / attendance 8） |
| **单跳 any-of 与多跳 all-of 分开统计** | `scripts/eval_retrieval.py:_summarize` docstring「⚠️ 单跳与多跳分开统计」 |
| **多跳三个指标** | 同上（`all_hit` / `partial_hit` / `doc_recall`；`partial_hit` 用于区分"完全找不到"vs"找到没找齐"） |
| **按 difficulty 分组** | 同上 docstring「简单题满分会把混合平均淹没」 |
| **冻结查询向量（对抗 embedding 浮点非确定性）** | 文件头:36-38 + `VECTOR_CACHE_FILE = eval/query_vectors.json` |
| **降级检测器** | `_DegradationCounter`（统计 rerank / embedding 失败，docstring 说明两类降级会静默改变指标） |
| 检索集负例 12 条 | 实测 `expect_documents` 为空 = 12 条 |
| **生成集构成** | `eval/gen_eval.jsonl` 实测 58 条：**answerable True 51 / False 7**；**difficulty easy 28 / hard 30** |

| **判分器防误判的编号口径** | `app/services/answer_grader.py:_JUDGE_SYSTEM`（"一个编号对应一整天资料原文…任意位置能找到依据就算对"） |
| 判分 fail-open | 同上 docstring:15-16 |
| **图谱集单独做的理由** | `scripts/eval_graph.py` docstring:3-6（"图谱通道完全不在 148 条里，图谱可用这句话没有证据"） |
| **图谱集三类 + 出处覆盖率** | 同上:8-15（entity / relation / negative；evidence 覆盖率验证"每条关系可回溯来源"） |
| 图谱集构成 | `eval/graph_eval.jsonl` 实测：entity 12 / relation 4 / negative 3 |

### 边界（如实交代）

- ⚠️ **LLM 判分器本身的可靠性没有验证**。我用它给忠实度打分，但**没有校验过这个判分器准不准**——没有人工标注一批"这句话是否被支撑"的对照集去测它的准确率和一致率。**用未验证的尺子量东西**，这是最本质的局限。
- ⚠️ **忠实度和引用准确率会随模型变**。换判分模型后这两项指标的历史数据不可比，因为标准变了。确定性指标没这个问题。
- **生成评测跑的是"检索 + 生成"全链路**，所以它的分数**不干净**——检索抖动会影响生成指标，排查问题时要先看检索评测。两者必须一起看。
- **148 条是我自己标的**，广度有限；`oss` 类占 39 条偏多，分布上可能偏向我抓的公开语料。
- **冻结向量解决的是评测可复现，但冻结意味着不再反映 embedding 模型的真实表现**。换 embedding 模型后必须重新冻结，否则旧向量和新模型不匹配。
- **图谱 19 条样本太小**（负例仅 3 条），只能支撑"能跑通、基本准确"，**不足以说"图谱有效"**。
- **三份评测集都是自标，没有第三方交叉验证**。评测集标准是我的标准。
- **没有做评测集过拟合的防护**。我调 chunk size、改 RRF 参数时用的就是这批评测集，**指标变好有可能只是拟合了这批题**，不是真实提升。这个问题我知道，理想做法是留一份不参与调参的 held-out 集，我还没做。

### 如果被追问，一句话版本

- **为什么判分尽量不用 LLM？**→ LLM 判分贵、有噪声、还引入版本漂移。能数出来的指标一律确定性判，LLM 只做"语义支撑"这类规则写不出来的判断。
- **多跳为什么不能和单跳一起平均？**→ 语义不同（all-of vs any-of），混算会让多跳的部分命中被平均掉，**失败信号被冲淡**。
- **冻结向量是为了什么？**→ embedding 服务端浮点不确定，不冻结每次跑都飘，**分不清是参数变化还是噪声**。
- **判分器自己准吗？**→ **我没验证过，这是最本质的局限。** 用未验证的尺子量东西。
- **调参会不会把评测集调过拟合了？**→ **会，这是我知道没解决的问题**，应该留一份不参与调参的 held-out 集。

## Q19. 你所有评测的结果是什么？recall@5 是多少，要点覆盖率是多少？

### 问

### 答（口述）

**我按三块报，每块都是实测脚本跑出来的。**

**第一块：检索侧，当前配置（174 篇语料、148 条评测集）。**

| 指标 | 值 |
|---|---|
| recall@5 | **0.992** |
| hit@1 | **0.975** |
| MRR | **0.983** |
| 简单题 hit@1（69 条） | **1.000** |
| 困难题 hit@1（51 条） | **0.941** |

**这套指标最能说明问题的是那个四级消融——我是把每一级关掉，量边际收益，不看"别人都说 rerank 好"：**

难例 hit@1：**纯关键词 0.706 → 加向量召回 0.804 → 加兜底门控 0.824 → 加 rerank 0.941**。

四个数逐级递进，而且每一步我都能解释失败案例。比如纯关键词为什么只有 0.706？因为我特意挑了**近义改写题**，刻意避开目标文档的词，让 BM25 失效——**不这么做，就测不出向量到底带来了什么**。又比如 `这个人想找什么方向的工作？` 被"王磊简历"抢走，因为同类简历都写"求职意向"——**失败是可解释的，不是噪声。**

**这里有个我要主动说的对比**：我最早在 14 篇文档上测，所有配置都接近满分，看不出差别。**扩到 174 篇之后，困难题 hit@1 才终于分开（0.824 vs 0.941）**。小语料上的满分是假象，测不出东西。

**最后我要主动交代一件事：还有一个调参结论是"没差异"。** `hybrid_top_k` 和 `rrf_c` 这两个参数，我**把语料扩到 12 倍后重测，依然没有差异**（rrf_c=10 只高 0.002 MRR）。**我没有编一个收益出来，而是明确记为"不调"。** 这比硬说"调参提升了 X%"诚实。

## Q20. chunk size 你做过测试吗？

### 问

chunk size 你做过测试吗？

### 答（口述）

**做过，而且这是我在调参上花力气最多的一项。**

先说为什么值得专门测：chunk size 是**影响召回最直接的参数**，而且它是"贵档"调参——改一个尺寸要**重新分块、重新嵌入、重建整条索引**，不是改个配置重启一下就行的。所以我写了个脚本把它自动化：对每个候选尺寸重建索引、跑一遍检索评测、汇总表格，跑完**自动恢复原尺寸**。

**结果是这样的**（174 篇文档、132 条用例、同一份冻结查询向量，每档重复跑两次）：

| chunk / overlap | 块数 | recall@5 | hit@1 | MRR | 复现 |
|---|---|---|---|---|---|
| 256 / 32 | 883 | **1.000** | **0.992** | **0.996** | 两次逐位一致 |
| **512 / 64（默认）** | 467 | 0.992 | 0.975 | 0.983 | 两次逐位一致 |
| 1024 / 128 | 274 | 0.992 | 0.967 | 0.979 | 单次 |

**结论是单调的：块越小，hit@1 和 MRR 越高**（0.992 → 0.975 → 0.967）。而且两次跑逐位一致——**单调加可复现，说明这不是随机噪声，是真实的方向性效应**。机制上也说得通：块数从 274 涨到 883，候选更细，向量匹配更精确。

**但我要重点讲的是：我测出来了，却没有改默认值。**

这是我觉得这个实验最有价值的部分——**知道和做之间还有一步判断**。三个理由：

**第一，幅度太小。** 相邻两档只差一两道题（120 条里），换一批问句完全可能翻过来。**一个只能靠特定问句复现出来的 1.7% 提升，不值得动生产配置。**

**第二，代价不小。** 256 的索引是 512 的 **1.9 倍**——883 块对 467 块。这意味着嵌入调用变多、存储变大、rerank 的候选量也跟着上升。而收益是 1.7%。**这笔账不划算。**

**第三，也是最关键的：评测集只有 120 条正例，不足以支撑一个"拿成本换两道题"的生产决策。** 要真正定案，得把评测集扩到几百条，或者做多组问句重采样看效应稳不稳定。**这些我都没做，所以我把这个权衡原样记录下来，而不是选一个看起来更好的数字。**

---

**顺便讲两个工程上的事，因为这类"贵档"实验特别容易踩坑。**

**一个是恢复机制。** 脚本跑完必须恢复原尺寸，如果恢复失败，索引就留在扫描到一半的尺寸上——**这是个静默损坏，不报错但检索质量已经变了**。我踩过一次：PG 资源紧张崩进 crash recovery，而挂在 `finally` 里的恢复逻辑复用了同一个已失效的会话，跟着一起失败。**教训是：恢复必须开全新会话 + 重试，结束时还要比对基线块数。** 我现在每次跑完都会打印"恢复校验通过：块数回到基线 467"。

**另一个是同轮修掉的一个真 bug。** 我有个全量重建索引的脚本，原先是 174 篇共用一个数据库会话——PG 一崩这个会话就永久失效。**实测崩一次，把后面 74 篇全部拖死，索引被留在混合尺寸**。改成每篇独立会话加重试之后，同样条件下只失败 1 篇，再跑一遍就收敛了。

**最后补一句诚实的话：这三档里 1024 我只跑了一次**，另外两档跑了两次验证可复现。所以严格说 1024 那一档的"单调"证据比另两档弱一点，虽然趋势是一致的。

### 事实锚点

## Q21. 系统稳定性如何？什么是并发？并发能力如何？如何证明？

### 问

你的系统稳定性如何？什么是并发？你的系统并发能力如何？如何证明？

### 答（口述）

**先说并发是什么。** 并发不是"同时有多少个用户在线"——那是注册数。**并发数是同一时刻真正在执行请求的数量**。比如 100 个人里 80 个在等 LLM 返回，那并发就是 20 而不是 100。**这个区分很重要，因为它决定了瓶颈在哪。**

**我的实测结论：单进程、mock 掉 LLM 的条件下，100 并发零失败。** 但**这个数字最不是重点，重点是它是怎么测出来的——因为我第一次测出来的结论是错的。**

---

**先讲方法论，因为我认为这才是回答"如何证明"的重点。**

我写了个压测脚本，但有两个刻意的设计：

**第一，把 LLM 和 Embedding 全部 mock 掉。** 因为**压测要测的是"我的系统在并发下什么行为"，不是第三方 API 的抖动**。mock 之后外部变量归零、不花钱、可复现、能进 CI。而且真实 API 的延迟方差会把连接池这类问题**掩盖掉**。

**第二，不只是测"成功还是失败"，而是真的去采样数据库连接。** 后台连上去查 `pg_stat_activity`，看应用到底占了多少连接。

**然后是第一个重要发现：第一轮跑出来"并发 20 时 5/20 失败"，p50 从 2.5 秒跳到 31.2 秒。** 31.2 秒正好等于连接池的超时时间——**这不是猜的，是服务端日志里拿到的一行确凿异常**。

**但我没有直接去调大连接池。** 这是我觉得整个过程里最关键的一个决定：**先问"连接被谁占着、占了多久"，而不是"池子够不够大"。**

给采样器加上状态分布，答案立刻清楚了：

```
峰值时刻：15 条连接（= 整池）全部被占用
  idle in transaction = 8,  active = 4,  idle = 3
空占连接的最后一条 SQL：
  ×6  SELECT kh_role.role_code FROM kh_role JOIN kh_user_role ...
```

**根因是 FastAPI 的生成器依赖会活到"响应结束"**——流式响应的话就是整个流结束。权限守卫用了它，于是**一次权限查询开的会话、事务、连接被占住整条链路**，包括后面几秒的检索和 LLM 生成。日志里那 6 条"空占连接"的 SQL，正好就是我的权限查询。

**修法两处，都不涉及调池**：权限守卫改用短生命周期会话，查完就还连接；后台摘要折叠把 LLM 调用移出会话块。

---

**结果对比，我认为最有说服力的是第二行：**

| 配置 | 池大小 | 并发 20 | 并发 40 | 并发 100 | 峰值连接 |
|---|---|---|---|---|---|
| 修复前 | 15 | **5/20 失败**，p50 31.2s | 18/22 失败 | — | 15 |
| **修复后（池不变）** | **15** | 20/0，p50 3.7s | 40/0，p50 3.3s | **100/0**，p50 6.0s | 15 |
| 修复后（默认池） | 30 | 20/0，p50 2.8s | 40/0，p50 2.1s | 100/0，p50 9.9s | 30 |

**池保持 15 一动没动，只修掉"连接跨外部调用持有"，100 并发就零失败了。** 而同一套代码在修复前、同样的池 15 下，并发 20 就崩。

**一句话总结：根因是连接的持有时间，不是池的容量。** 加池只是把"占着等"的容量买大一点。

**顺便说一个我要主动纠正的读法**：峰值连接修复前后都是"等于池上限"（15 或 30），**说明池被用满了，但"用满"不等于"失败"**。所以这个数字**不该被讲成"优化后降下来了"**——它"降下来"只是因为池本来就更小。这种数字上的自我纠正是我觉得比结论本身更重要的东西。

---

**还有一个坑我想讲，因为它直接推翻了旧文档里的数字。**

我最早版本的采样器，为了"避免采样器自己污染指标"，**复用一个长事务会话**去查。结果 `pg_stat_activity` 的可见行集**冻结在事务开始时的快照**上。实测：**同一时刻新连接能看到 15 条应用连接，那个长会话里始终只看到 1 条。**

于是旧文档里那个"31 → 2"就是这么来的——**它不是测量值，是首帧快照值**。**我的"峰值连接从 31 降到 2"这个结论是假的，整条结论都被作废了。** 后来改成每次采样新签一条 AUTOCOMMIT 连接、按 `application_name` 只统计被测实例，这个数字才可复算。

**这件事我觉得比修复本身更值得说：测量方法错了，测得再认真也是错的。**

---

**稳定性这块我还想讲一个真实故障排查**，因为它回答的是"系统稳不稳"而不是"能扛多少并发"。

有用户报"图谱页一直转圈 + 500"，我查出是**三层问题叠在一起**：

1. 请求挂满 **60 秒**才返回——因为没设连接超时，asyncpg 默认就是 60 秒
2. 最后返回**不透明的 500**——连接类异常没被单独处理
3. **连不碰数据库的 `/docs` 接口也挂死**——启动时强依赖 PG，30 次重试后进程退出，但 reloader 父进程还握着监听套接字，成了"**端口有人听、永远没人答**"

三层各修一处：显式设 5 秒连接超时（快速失败）、连接类错误映射成 503 加 Retry-After、启动建表失败改成**降级启动**而不是退出。

**验证是真实停掉 PG 测的**：停 PG 后 `/docs` 返回 200（非 DB 接口不受影响）、`/graph/overview` 返回 503 且 0.023 秒返回；**恢复 PG 后不用重启应用，连接池自己就恢复了**。

**但这个取舍我也要说清楚**：降级启动会**掩盖"生产环境配错库地址"这类硬错误**——进程不退出、不触发重启。所以 `/health` 是 liveness 永远 200，**真正的 readiness 应该看 `database` 字段**，不能靠进程退出来发现问题。

### 边界（如实交代）

- ⚠️ **这是单进程、mock LLM、本开发机的实测结果**。真实环境有 LLM 的长尾延迟、多进程部署、以及 Docker VM 内存限制（自托管 Langfuse 那套就吃掉 2.6 GB，曾把 PG 后端 OOM 杀掉）。**100 并发零失败不能直接搬到生产。**
- **mock 掉 LLM 是刻意的，但也意味着我测不出真实 LLM 延迟对并发的影响**。真实情况下并发瓶颈更可能在 LLM 配额而不是连接池。
- **峰值连接数是采样值，不是精确峰值**。采样间隔内的瞬时峰值可能捕捉不到。我按 `application_name` 只统计被测实例，是为了排除同库开发实例和 GUI 的干扰——**但这也意味着被测实例之外若有真实流量，测不到。**
- **只压了对话接口** `/ai/chat`，**没有覆盖文档上传、索引重建这些重 IO 路径**。上传大文件时的并发行为我完全没测。
- **降级启动的隐患我承认没完全解决**：掩盖"配错库地址"这类硬错误。我用 `/health` 的 `database` 字段来区分，但那需要外部探针真的去读这个字段——**没有探针配置的话等于没做**。
- **单机单进程**，没有测过多副本部署下的表现，也没有测过服务重启期间的错误处理。
- 那次 OOM 导致 PG 进 crash recovery 的事，说明**我的开发环境资源是紧的**，这本身也是压测结论可靠性的一个限制。

### 如果被追问，一句话版本

- **100 并发零失败是怎么证明的？**→ 脚本自己起 mock LLM 和独立实例、N 路并发打真实接口、后台采样 `pg_stat_activity`；**最有力的证据是池保持 15 不变、只修掉"连接跨外部调用持有"就从 20 并发 5 失败变成 100 并发零失败。**
- **为什么不直接调大连接池？**→ 因为**根因是持有时间不是容量**。池调大只是把"占着等"的容量买大一点，同等容量下修复后能跑 5 倍并发。
- **你的数字可靠吗？**→ **我推翻过一次自己的数字。** 旧文档"峰值连接 31→2"是采样器复用长事务会话导致的假值（行集冻结在事务开始快照），**整条结论作废**，改成每次新签 AUTOCOMMIT 连接后重测。**测量方法错了，测得再认真也是错的。**
- **并发和在线用户数的区别？**→ 并发是同一时刻真正在执行的请求数。100 人里80 个在等 LLM，并发就是 20。**这个区分决定瓶颈在哪。**
- **稳定性怎么证明？**→ 除了压测，我**真实停掉 PostgreSQL 验证过**：非 DB 接口 200、DB 接口 503 且 0.023s 返回、恢复后不重启应用连接池自愈。**但降级启动会掩盖配错库地址，这个取舍我承认没完全解决。**
