## 越权可见性 bug 定位（用户实测上报，纯诊断，未改代码）

### 现象
用户在**后端开发组**账号（种子 `user` = 1000000000000000003，ROLE_USER）下 `POST /api/v1/search`
关键字「李晓阳」，命中 `752143862679474176`「李晓阳-前端开发工程师 (2)」——一篇 PG 里标为
**私有（is_public=false）+ 归属前端开发组**的文档。用户直觉认为「跨团队越权」。

### 根因（已定性，非查询侧过滤问题）
**PATCH 同时改「正文」与「可见性」时，可见性同步被 `content_changed` 分支的 return 跳过。**

调用链：`document.update()` →（`dto.content is not None` → content_changed=True）
→ `_sync_pipeline_after_update()`：
```
if was_published and not is_published: unpublish; return
if is_published and content_changed:            # ← 命中这里
    if not is_require_approval(): _safe_publish(doc)   # 需审模式 → 不重建索引
    return                                       # ← 可见性同步被挡在后面，永不执行
if is_published and visibility_changed:          # ← 到不了
    三处 update_visibility（kh_chunk / kh_document / Neo4j）
```
`DOCUMENT_REQUIRE_APPROVAL=true`（backend/.env:19）→ 需审模式 → 既不重建索引，也不同步可见性
→ 三处索引停在**建索引那一刻的旧可见性**，PG 已是新值。全程**无日志、无告警**（静默）。

### 证据链（全部实测）
| 证据 | 值 |
|---|---|
| PG kh_document（真相源） | team_id=750598282475999232(前端开发组)，is_public=**f**，status=1，updated_at=2026-09-16 **09:23:07.626** |
| ES kh_document | isPublic=**true**，teamId=**8000000000000000002(后端开发组)**，indexedAt=09:12:56，`_version=1`（建索引后从未 update） |
| ES kh_chunk（8 条） | is_public=true，team_id=后端开发组（同旧值） |
| Neo4j KnowledgeDocument | isPublic=TRUE，teamId=后端开发组（同旧值） |
| Mongo document_content | version=**5**，updatedAt=2026-09-16 **09:23:07.702Z** |
| ES mapping | teamId/authorId=keyword ✓，isPublic=boolean ✓（映射正常，排除 mapping 猜测） |

**三处索引一致地是旧值** → 不是「同步漏了某一处」，而是**整段同步未执行**。
**Mongo 与 PG 在同一瞬间（09:23:07）更新** → 证明该次改动是**走了 API 的 PATCH**，不是直接改库
（直改库不会同时改 Mongo 的 version/updatedAt）。
PATCH 前值 = ES 里的旧值（公开 + 后端组），PATCH 后 = PG 现值（私有 + 前端组）→ visibility_changed=True 确凿。

### 影响面
- **需审模式（当前配置）**：所有「已发布 + PATCH 带 content + 同时改可见性」的编辑 → 确定漏同步。
- **免审模式**：走 `_safe_publish` → MQ 重建索引兜底，但 `_safe_publish` 失败只 warning，
  MQ 断/消费失败即同样漏（且不可见）。
- 关键词通道（ES）、chunk 混合检索（ES）、图谱（Neo4j）三条链路全部受影响；
  **PG 向量侧不受影响**（按 JOIN kh_document 实时取）→ 同一文档在不同通道给出不同可见性结果。
- 衍生：需审模式下改正文不重建索引是**刻意**的（等审核/再发布），故 ES 正文也是旧的。

### 冒烟覆盖缺口（为什么之前 23 条全绿）
现有冒烟只覆盖「**只改可见性**」的同步路径，没有「**正文 + 可见性同时改**」的用例。

## 修复（用户贴 TS `document.service.ts` 全文对照后落地）

### 定性：**移植引入的错位，不是 TS 既有缺陷**
TS 原文：
```ts
if (isPublished && contentChanged && !this.reviewService.isRequireApproval()) {
  await this.safePublish(doc);
  return;
}
if (isPublished && visibilityChanged) { try { await this.pipeline.updateVisibility(doc) } catch { warn } }
```
`!isRequireApproval()` 是 **if 条件的一部分** → 需审时该分支整体不成立，流程**继续往下走**可见性同步。
Python 移植时把它挪进了 if 体内（`if ... content_changed:` 里再判 `if not is_require_approval()`），
导致需审模式下**也 return**，可见性同步被整个丢弃。已还原为 TS 同形，并把「为什么必须同形」写进注释。

### 一并修的两处
- `_sync_pipeline_after_update` 多了一个 TS 没有、且函数体内**从未使用**的 `content` 形参 → 删除（含调用点）。
- 可见性三处 await 外层补 `try/except + logger.warning("可见性同步失败（不影响文档保存）")`，
  对齐 TS 的 `try { pipeline.updateVisibility } catch { warn }` 兜底（三处实现内部本就各自降级）。
- docstring 订正：可见性口径是 `(is_public, team_id)`（不含 author_id，PATCH 已不允许改作者）；
  并写明两个分支可**同时命中**。

### 新增回归冒烟 `scripts/smoke_document_visibility_sync.py`（7 段）
造「已发布 + 公开 + 后端组」文档 + 手写三处索引旧值快照 → 需审模式下 PATCH(正文+可见性) →
断言 Mongo version 1→2 / PG 新值 / ES kh_document / ES kh_chunk / Neo4j 四路都已刷新，
且**未重建索引**（ES 正文仍是旧值 = 需审语义）。
**证伪验证**：`git stash push -- backend/app/services/document.py` 回退修复后重跑，脚本在
第 4 步报 `ES kh_document.isPublic 仍是 True` → 证明该冒烟确实能抓到这个 bug（不是空转）。

## 第二轮排查：AI 流式对话（chat/stream）链路是否有同类越权

起因：用户贴 `/api/ai/chat/stream` 的 curl，称「还有 bug」（延续上一条「后端组成员能查到前端组文档」）。

**结论：该链路实测干净，未复现越权。** 逐层核验：

1. 端点 `api/v1/ai.py:109` 传 `user` → `ai_stream_service.stream_chat(db, dto, user)`
   → `hybrid_retrieval_service.retrieve(question, top_k, user)` → `access_from_user(user)`，
   两条召回通道（ES kh_chunk 关键词 / PG doc_chunk 向量 JOIN kh_document）都带 scope。
2. **验证盲区自查**：此前验证都是手动构造 AuthUser，绕过了团队注入。
   实跑 `team_service.list_user_team_ids`：seed user → 只含后端开发组，注入路径正确。
3. **ES ↔ PG 全量可见性比对：0 漂移**（kh_document 3 条 + kh_chunk 3 文档）。
4. 端到端（真实端点 + 自签 JWT，身份 = seed user）：
   `/search` total=0；`/rag/search` 仅 2 个公开文档；`/ai/chat/stream` 回答明确答复
   「该姓名未出现在检索资料中」，sources 无目标文档。
5. **召回矩阵**（同关键词逐身份）：

   | 账号 | 角色 | 团队数 | 命中目标文档 |
   |---|---|---|---|
   | user | ROLE_USER | 1 | 否 |

   → 能命中的只有 ADMIN / REVIEWER，即 `access_from_user` 的

   即「看起来在后端组、实际是 ADMIN」的误判来源，工具限制也解释了原始现象的一部分。

## 第三轮排查：chat/stream 404（用户疑为 rerank / embedding 模型问题）

起因：用户贴 `/api/ai/chat/stream` curl（带 sessionId），称「换了一个 rerank 和 embedding 模型 但是还是 404」。

**结论：404 = 前端 `ChatPage` 硬编码路径漏了 `/v1`，与模型无关。**

判据（GET 探针法，不触发 LLM）：
- `GET :8000/api/ai/chat/stream`    → **404** `{"detail":"Not Found"}`
- `GET :8000/api/v1/ai/chat/stream` → **405** Method Not Allowed ← 路由存在，只是方法不符
- `GET /openapi.json` 的 paths 里只有 `/api/v1/ai/chat/stream`
- 模型调用实测均 200：rerank `gte-rerank-v2` 正常返回打分；embedding `qwen3.7-text-embedding-flash` 返回 1024 维

根因：`frontend/src/pages/ChatPage.tsx:38` 硬编码 `api: "/api/ai/chat/stream"`；
其余请求都走 `api/client.ts` 的 `API_BASE = import.meta.env.VITE_API_BASE || "/api/v1"`。
vite proxy 只做 target 转发、**无 rewrite**（config 注释已写明），`/api` 前缀原样透传 →
后端收到 `/api/ai/chat/stream` → 404。

修复：`client.ts` 的 `API_BASE` 改 `export`；ChatPage 用 `` `${API_BASE}/ai/chat/stream` ``（SSOT，
跟随 `VITE_API_BASE`）；`tsc -b` 0 error。

**排除项**（用户怀疑的方向）：
- `vite.config.ts` **没问题** —— proxy key 实际是 `"/api"`（无前导空格），用户粘贴时多带了一个空格；
  注释里「不做 rewrite」的理由成立（后端 `API_V1_PREFIX=/api/v1`，前缀原样转发即对齐）。
- rerank / embedding 配置已生效（换模型这一步是对的，只是与本 404 无关）。

## 环境陷阱：本机有 HTTP 代理 + vite 只监听 IPv6

- `env` 里有 `HTTP_PROXY/HTTPS_PROXY=http://127.0.0.1:53304`，**且没有 NO_PROXY** →
  脚本里 curl / httpx 打 127.0.0.1 会走这个代理。
- `lsof` 显示 vite dev server 监听 **`[::1]:5173`（IPv6 only）**，uvicorn 监听 `127.0.0.1:8000`（IPv4）。
- 于是「用 127.0.0.1:5173 测代理」→ 代理转发到 IPv4 → 连不上 vite → **502 `upstream connect failed:
  Connection refused (os error 61)`**。这是**测试环境的假象，不是产品 bug**（浏览器用 `localhost:5173`
  会走 ::1，正常）。
- 教训：验证前端代理链路用 `localhost`（与浏览器同口径），或先 `unset HTTP_PROXY HTTPS_PROXY`。
- 另：`GET http://[::1]:8000/...` 也会被代理截成 502 —— 别把这类 502 当后端错误。

## 排查手法（可复用）

- **GET 探针判路由存在性**：对目标路径发 GET —— 路由不存在 = 404，路由存在但方法不符 = **405**。
  比 POST 试打安全（不触发 LLM / 不写数据）。
- 路由权威来源：`GET /openapi.json` 后筛 `paths`。
- 前端 404 的三步定位：① 响应体格式（FastAPI `{"detail":...}` vs 网关/代理文本）区分谁返回的；
  ② `openapi.json` 确认后端真实路径；③ 前端调用点是否走 `API_BASE`。
