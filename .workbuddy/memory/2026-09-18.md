### 保真点（写代码时逐条对齐，改时勿破）
- 窗口 = `[m for m in msgs if is_working_message(m)][-max:]` → **只留最近 N 条**。
- 只存 human/ai 原文：system（Mem0）/ tool（检索结果）不进窗口；两条来源
  （Redis 热窗口、DB 回填）共用 `is_working_message` 同一口径。
- `try_load` 任何异常 → WARN + `None`（语义 = 请回落数据库），绝不向上抛；
  `save` / `clear` 失败只 WARN（缓存不可用不能影响对话与落库）。
- **`save([])` 后 `try_load` 返回 `[]` 而非 `None`**（对齐 TS：值是 `"[]"`，真值判断过关
  → `messages_from_dict([])` → `[]`）。调用方不能把 `[]` 当 miss，否则白白回填一次。
- key 形态 `{PREFIX}:{userId}:{sessionId}:messages`，`str()` 归一（防 int/str 两种雪花
  形态长出两个 key → 「存了却 miss」）。
- TTL 默认 86400s；序列化 `ensure_ascii=False`（对齐 `JSON.stringify` 不转义中文）。

### 踩坑 / 加固点
- ⚠️ **冒烟必须先显式 `ping()` 探活**：`save`/`clear` 吞异常只 WARN，Redis 没起时

### 按源码核实（不靠记忆）——与 JS SDK 的实质差异
装 `mem0ai==2.0.20`（`uv add`，+11 包：qdrant-client / posthog / numpy / protobuf /

| 能力 | TS（JS SDK） | Python 2.0.20（v3 API） |
|---|---|---|
| 客户端 | `new MemoryClient({apiKey, host?})` | `AsyncMemoryClient(api_key=..., host=...)`；**无 key 直接 raise**（先判空再构造） |

| 写入 | `add(msgs, {userId, runId, customInstructions})` | `await client.add(msgs, filters={'user_id':…,'run_id':…}, custom_instructions=...)` |

### 3. Mem0 实证纠错（**前一轮的结论写错了，已改正**）
前一轮「`add` / `delete_all` 的实体 ID 也要放 `filters`」是**照 SDK 类型注释推断的，错了**。
这轮用户把 `MEM0_API_KEY` 填上后，冒烟第 6 步从 SKIP 变成真跑，立刻暴露 400。实测结论：
| 方法 | 实体 ID 位置 | 实证 |
|---|---|---|
| `search` | **必须** `filters={...}` | 放顶层被 SDK `ENTITY_PARAMS` 白名单 raise（客户端拦） |
| `add` | **必须**顶层 `user_id=` / `run_id=` | 包 `filters` → 400「At least one entity ID is required」 |
| `delete_all` | **必须**顶层 | 包 `filters` → 400，且 dict 被 httpx `str()` 塞进 URL（`filters={'user_id': …}` 单引号）连 JSON 都解析不出 |
`get_all` 走 POST + JSON body，`filters` 正常，**run_id 过滤实测有效**（同 user 4 条 → 命中 1 条）。

**最严重的一条**：`delete_all(user_id=…, run_id=…)` **完全忽略 run_id，直接清空该 user 的全部
记忆**。实测：删除前 user 层 4 条 / 本会话 1 条 / 其他会话 1 条 → 调用后 0 / 0 / 0，且 120s
内不复原（排除了「异步延迟」的解释）。也就是说 TS 的 `clearSession` 在当前云 API 上等于
「删一个会话 → 顺手抹掉这个用户的全部长期记忆」，而且只留一行 WARN，完全不会被发现。
→ `clear_session` 刻意改为 `get_all(filters={user_id, run_id})` 列 id → 逐条 `client.delete(id)`
（实测只删目标：4 → 3）。

另一条平台特性：`add()` 是**异步抽取**，返回 `{'status':'PENDING'}`，实测 6~9s 后才可检索；

## 日志初始化：logger.info 看不到的根因（21:00）

用户报「logger.info 的信息怎么都看不到输出」。根因：**`app/` 里没有任何日志初始化**。

- Python logging 默认 root = **无 handler + level=WARNING**；业务 logger 按名字取
  （`getLogger("DocumentService")`）→ effective level 继承 root 的 WARNING →
  **info 全部被丢弃**；warning/error 能出现是 `logging.lastResort` 兜底
  （裸 message，无时间戳 / 无级别 / 无 logger 名）。
- uvicorn 不救场：实测其默认 `LOGGING_CONFIG` 里 `"" not in LOGGING_CONFIG["loggers"]`
  为 True——**只声明 `uvicorn` / `uvicorn.error` / `uvicorn.access`，完全不管 root**。
  FastAPI 同样不管。所以「WARN 能看到、INFO 看不到」是必然结果，与业务代码写法无关。

修复：新增 `app/core/logging.py`（`setup_logging()` 走 dictConfig），`main.py` 顶层调用。

关键决策（全部实测）：

| 点 | 做法 | 为什么 |
|---|---|---|
| `disable_existing_loggers` | **必须 `False`** | 置 True 会禁掉 uvicorn 在 import app **之前**已建好的三个 logger → 启动日志整批消失且不报错 |
| uvicorn 三个 logger | handlers 清空 + `propagate=True`，**刻意不写 level** | 并入统一格式；省略 level 才能让命令行 `--log-level` 继续生效（实测 `--log-level warning` 时 uvicorn 的 INFO 如期消失） |
| root 已有 handler | **只 `setLevel`，不覆盖 formatter** | 不越权改冒烟脚本 / pytest / 容器的既有配置 |
| `LOG_LEVEL` 拼错 | 回退 INFO，**不抛异常** | 日志级别写错不该让服务起不来（与 `CHAT_SHORT_MEMORY_MAX_MESSAGES` 那类「非法即报错」刻意不同） |

验证矩阵 6 项全过：INFO 输出 / DEBUG 被过滤 / `LOG_LEVEL=DEBUG` 生效 /
`LOG_LEVEL=verbose` 回退 INFO 不崩 / root 已有 handler 时不覆盖 formatter /
`mypy app/` **108 files 0 issue**。另真实启动 uvicorn 两次，确认启动日志与 access log
都已统一为 `2026-09-18 21:08:27 INFO  [uvicorn.access] 127.0.0.1:59547 - "GET / HTTP/1.1" 200`。

**回退法证伪**：临时注释 `main.py` 的 `setup_logging()` → root 回到
`handlers=[] level=WARNING`、`isEnabledFor(INFO)=False`、WARN 变裸文本；恢复后正常。
确认是该行在起作用，而不是别的 import 顺带配了日志。

外部行为变化：**import `app.main`** 的冒烟（`smoke_ai_sessions` 等）现在会输出业务
INFO（此前静默）。实测 4 个冒烟全绿，无误伤。而自带 `logging.basicConfig` 的 4 个脚本
（smoke_role_api / smoke_auth_email_routes / smoke_document_review_routes /
smoke_email_flow）经查**不 import app.main** → 行为完全不变。

`--reload` 的一个固有时序（**未处理**，如实记录）：reloader 主进程的
`Will watch for changes` / `Started reloader process` 仍是 uvicorn 原生格式，
因为那几行打在我们 import app 之前；子进程（真正跑 app 的）已统一。收益（3 行日志）
远小于引入独立 log-config 文件的复杂度（且会造成第二真相源）。

顺带发现（**未改**，待拍板）：4 处 logger 用 `__name__` 而非类名，输出会是
`[app.utils.parsers.pdf]` 而非 `[ClassName]`——`file_parser.py` → `FileParserService`、

## SQL 日志刷屏：echo 绕过 logging 级别（21:28）

用户报 `INFO [sqlalchemy.engine.Engine] SELECT kh_ai_session...` 这类 SQL 不要输出。
根因**不是**日志级别没配好，而是 `db/session.py` 的 `echo=settings.DEBUG`（`DEBUG` 默认
True，而它本职是 /docs 开关）—— 属于「一个开关管两件事」的错耦合。

### 关键机制（读 `sqlalchemy/log.py` 源码 + 实测）

`InstanceLogger.log()`：

```python
selected_level = self._echo_map[self.echo]     # echo=True → logging.INFO
if selected_level == logging.NOTSET:           # 只有 echo 为假才回落
    selected_level = self.logger.getEffectiveLevel()
if level >= selected_level:
    self.logger._log(level, msg, args, **kwargs)   # 绕过 Logger.isEnabledFor()
```

⇒ **echo 为真时判定级别取自 echo 映射、完全不读 effective level，且直接调 `_log()`**。
所以 `_NOISY_LOGGERS` 里的 `sqlalchemy.engine` 是**假开关**（实测调到 WARNING / CRITICAL
均照样输出）—— 唯一有效做法是从引擎侧关。

反向实测：`echo=True` 时 SQLAlchemy 还会经 `_add_default_handler()` 自挂一个
`StreamHandler(sys.stdout)`，与 root handler 形成**双份输出**（一份裸格式 `INFO sqlalchemy.engine.Engine ...`、
一份我们的 `INFO  [sqlalchemy.engine.Engine] ...`）；`echo=False` 时该 logger handlers=0。

### 改动（4 个文件 + 1 skill）

| 文件 | 改动 |
|---|---|
| `app/core/config.py` | 新增 `DB_ECHO: bool = False`（注释写清「为什么与 DEBUG 解耦」+「级别压不住 echo」） |
| `app/db/session.py` | `echo=settings.DB_ECHO` |
| `.env` / `.env.example` | 同步 `DB_ECHO=false` |
| `app/core/logging.py` | `_NOISY_LOGGERS` 移除 `sqlalchemy.engine`（假开关）+ 说明注释 |
| 4 个冒烟脚本 | 注释订正：原写「engine 以 echo=settings.DEBUG 创建」已过时 → 改为「兜底：DB_ECHO 打开时手动压掉」 |

### 验证

| 场景 | 结果 |
|---|---|
| 默认 `DB_ECHO=false` + 真实查询 | SQL 行数 **0** |
| 真实 uvicorn + `GET /api/v1/ai/sessions?page=1&pageSize=10`（用户报的那条 SQL） | HTTP 200，日志 SQL **0** 行，业务 INFO / 启动日志 / access log 全正常 |
| `DB_ECHO=true` | SQL 回来（20 行）→ 开关可用、没被焊死 |
| `LOG_LEVEL=DEBUG` + `DB_ECHO=false` | SQL 仍 0 行 → 与级别真正解耦 |
| 回退法证伪（改回 `echo=settings.DEBUG`） | SQL 20 行复现 → 确认是这处改动起效 |
| `mypy app/` | 108 files, 0 issue |
| 冒烟回归 4 个 | 39 + 14 + 8 断言全绿，SQL 行均 0 |

1. `api/auth_route.py:225` 消息文本里手写了 `[AuthRoute]` 前缀 → 实际输出
   `[AuthRoute] [AuthRoute] 鉴权守卫已覆盖…`（真实启动日志里看到）。已删除前缀。
   教训：**消息文本绝不写 `[ClassName]`**，格式里的 `%(name)s` 已提供。
