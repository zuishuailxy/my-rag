## 追加核验：search 链路完整性（`search-index.service.ts` 全文 + `search.controller.ts`）

用户贴完整 TS 问「看看完整没有」。**结论：除状态码口径外全部对齐。**

**Service 侧逐项**：
- `onModuleInit`（自建 `new Client` + `cluster.health` + 失败置 null）→ 等价物 `app/db/es.py:es_service.start()`；客户端单例复用是既定刻意差异（文件头已注释）。`ELASTICSEARCH_ENABLED !== 'false'` ↔ `settings.ELASTICSEARCH_ENABLED: bool = True` ✓
- `indexDocument` ✓（`String(doc.id)` / `indexedAt: new Date().toISOString()` ↔ `_utc_iso()` / `refresh: true`）
- `updateVisibility`：**实现手段差异**——TS 用 `es.update({id, doc})`（写 `null`，id 不存在则 404 被 catch warn）；Python 用 `update_by_query` + script（写空串 `""`，id 不存在则 updated=0 静默返回）。语义等价（`terms` 都命中不到），代码已注释
- `deleteDocument`：TS 仅在 message 不含 `404` 时才 warn，但**两种情况都打**「搜索索引已删除」；Python 遇 `NotFoundError` 直接 debug + return（不打 info）—— 仅日志差异
- `ensureEsIndex`：TS `indices.exists` → `indices.create`（mapping **11 字段、无 settings**）；Python `ensure_index` 同结构 + `BadRequestError` 幂等兜底，mapping **17 字段**（多 viewCount/likeCount/commentCount/createdAt/updatedAt/indexedAt）+ settings `1 shard / 0 replica`（单节点防 yellow，已注释）。无害：TS 靠动态映射同样会建出这些字段
- `ensureVisibilityMapping` ✓ 三字段 `putMapping` 完全一致
- ⚠️ **调用时机差异**：TS 在 onModuleInit 里调一次 `ensureEsIndex` + `ensureVisibilityMapping`；Python 在 main lifespan 只调两者的 `ensure_visibility_mapping`，`ensure_es_index` 改在 write/search 前调（幂等、代价一次 HEAD）。功能等价

**Controller 侧**：`@Post()` + `@RequirePermission(search)` + `@CurrentUser` + `accessFromUser(user)` → Python 全对齐。

**唯一实质差异 = 状态码**：TS `@Post()` 是 NestJS 默认 **201**；Python 查询类 POST（`/search`、`/search/hybrid`、`/rag/search`、`/ai/chat`）统一 **200**，写操作才显式 201（auth/users/role/document/ai sessions）。
→ **用户 09-15 拍板：保持 200 + 注释文档化**（查询语义更贴切；前端封装的 `post` 只判 2xx，无契约影响）。已在 `api/v1/search.py` 与 `api/v1/ai.py` 模块 docstring 写明。

**顺带标注**：`/search/hybrid` 是 Python 独有端点（TS `search.controller.ts` 只有 `@Post() /search`；chunk 级混合检索在 TS 侧属 `AiController` 的 `POST /rag/search`，本项目两者都保留、共用 `hybrid_retrieval_service.retrieve`）。该端点自 09-04 方案 B 起存在，已在 docstring 注明来源。
