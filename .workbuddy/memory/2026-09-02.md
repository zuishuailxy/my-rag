## 三层守卫覆盖审计（19:40，回答「原来的三层 guard 都实现了吗」）

- **结论：三层全部实现且生效。** ① JwtAuthGuard → `AuthRoute` 默认全拦 + `@public()`；② RolesGuard → `@roles(...)`；③ PermissionsGuard → `require_permission()` 依赖。
- 运行时审计（临时脚本，跑完即删）：56 条 APIRoute **全部**是 AuthRoute（check_route_classes 确认 count=56 无裸奔）；分布 = 公开 8 / 仅登录 18 / 登录+角色 18 / 登录+角色+权限码 12。第三层挂在 permissions 8 条（system:permission[:create|:edit|:delete]）+ role 2 条（system:role）+ user 2 条（system:user）。
- **⚠️ 重要架构事实：第三层当前被第二层「遮蔽」，不会独立拒绝。** 12 条挂 require_permission 的端点**同时**都有 `@roles(ADMIN)`；AuthRoute 的 handler 里角色检查在 `original_route_handler(request)` **之前**（依赖系统此时才跑），故非管理员在第二层就 403，管理员又因 ADMIN_OPERATION_PERMISSIONS 自动继承必然放行。实测：给 ROLE_USER 用户直授 `system:user` 后调接口仍 403。**这是 TS 同款设计（非 blanket 放行），属忠实移植，不是 bug**——但若将来要给非管理员按权限码开放端点，必须先摘掉该端点的 `@roles(ADMIN)`。
- 第三层本身**功能正常**（隔离验证：未授权用户 → 403；直授 system:user 后 → 放行），现有冒烟里的 403 全部来自第二层，故第三层此前无独立用例覆盖。
- **坑（审计脚本踩到）**：FastAPI 的 `params.Depends` 属性是 **`dependency`** 不是 `call`；`route.dependencies` 才是路由级依赖（`route.dependant` 是解析后的）。另外 `check_route_classes` 挂在 lifespan 里，**冒烟脚本不挂 lifespan 所以自检平时跑不到**。
- **坑（临时脚本）**：`make_access_token` 在 `scripts/smoke_auth.py`（非 app.core.security）；项目只有 `async_session_factory`，**没有同步 SessionLocal**。
