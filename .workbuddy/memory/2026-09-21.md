### 复查结论（逐点核对，无阻断问题）

| 检查点 | 结论 |
|---|---|
| 折叠边界 `id < window_start_id` 用严格小于 | ✓ 查询 `order_by(id.desc())` → `window[-1].id` 是窗口内**最旧**那条，仍在窗口里（原文保留），不能被折进摘要 |
| 水位比较用 `id > 水位`（非 `≥`） | ✓ 等于水位的上次已折过 |
| `len(window) < limit` 早退 | ✓ 消息还没超窗口时无事可做 |
| 幂等 | ✓ `window_start_id <= 水位` 早退，重复 fold 水位/摘要都不动（冒烟第 7 步实证） |
| 独立表 vs 给 `kh_ai_session` 加列 | ✓ `Base.metadata.create_all` 只 `CREATE TABLE IF NOT EXISTS`、不 ALTER 已有表 → 独立表在存量库能自动补建 |
| 存量库结构与 init.sql | ✓ 逐列核对（bigint/text/timestamp、NOT NULL、默认 `''`/`0`/`now()`、PK + FK `ON DELETE CASCADE`） |
| 删会话清理 | ✓ 由三处变四处（短期 / 长期 / 摘要 clear），DB 侧虽 CASCADE 仍显式删 |

### 复查发现的小问题（未改，待用户拍板）

1. `ChatSessionSummaryService._locks` 是 `dict[str, asyncio.Lock]`，`setdefault` 只增不减 →
   每会话一个 Lock 常驻，会话数无上界 → 长跑进程慢泄漏（单个 Lock 很小，属量级可控但应清理）。
2. `save()` 的 upsert 是「先 `db.get` 再 `add`」，并发撞主键时第二个只 WARN 丢写：
   `fold` 有每会话锁兜住主路径，`clear` 没有（与 `fold` 并发时可能丢失一侧写入）。
